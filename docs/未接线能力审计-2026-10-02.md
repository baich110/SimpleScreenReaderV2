# 未接线能力审计（2026-10-02）

> 方法：扫描所有框架类的公开方法，找出「实现了但从未被调用」的能力。
> 这类问题不会编译报错，属于**静默失效**，是工程可维护性的主要隐患。

## 发现并修复（3 项）

### BUG-A｜屏幕参数从未初始化（P0，影响排序正确性）

**症状**：`NodeOrderComparator.initScreen()` 从未被调用，
排序算法一直使用硬编码的 `screenWidth=1080, screenHeight=1920`。

**影响**：排序算法用屏幕尺寸算三个阈值：
- `threshold02H = 屏高 * 0.2`
- `threshold03H = 屏高 * 0.3`
- `threshold10dp = 10dp → 像素`

不初始化 → 在非 1080×1920 的设备上（**绝大多数现代手机**）判定系统性偏差
→ 节点排序错误 → **焦点顺序错乱**。

**天坦的做法**：`C1423r.f23902d.M(this)` 在 4 处调用：
① 横竖屏切换 ② 服务重启/恢复 ③ 服务连接 ④ 窗口变化重建。

**修复**：
- 新增 `NodeOrderComparator.initFromContext(context)`（从 `displayMetrics` 读尺寸与密度）
- 服务连接时调用
- **新增 `onConfigurationChanged` 覆盖**（原来是缺失的，横竖屏切换后参数不更新）

---

### BUG-B｜语音输入静音闸门未接线（P0，影响用户体验）

**症状**：`AudioFocusManager.shouldMute()` 实现完整（检查前台是否语音输入法 +
麦克风是否被占用），但**从未被调用**。

**影响**：用户用语音输入时，读屏仍在朗读，**把用户说的话盖掉**。
这是盲人用户高频使用的场景。

**天坦的做法**：`SpeechController` 用
`AudioManager.getActiveRecordingConfigurations().size() != 0` 检测录音状态
（1 秒缓存），命中则不出声。

**修复**：
- `SpeechEngine` 新增 `speechGate` 回调（所有播报入口统一受控）
- 服务里绑定 `speech.speechGate = { audioFocus.shouldMute() }`
- 闸门放在 `speakInternal()` 最前面，避免漏判任何播报路径

---

### BUG-C｜滚动状态标记未接线（P1，导致导航拦截失效）

**症状**：`FocusManager.onScrollStart()` / `onScrollEnd()` 从未被调用，
`isScrolling` 标志永远是 false。

**影响**：`FocusManager.moveFocus()` 里的「滚动中同方向导航直接吞掉、
反方向取消滚动」这段逻辑（天坦 `M6.h.D()` 的核心保护）**完全失效**。
后果：自动滚动过程中用户继续滑动 → 焦点与滚动打架 → 跳位。

**天坦的做法**：`M6.h` 用 `f6006f` 标志 + `f6008f` 方向，在 `D()` 开头拦截。

**修复**：`handleScroll()` 里根据 `scrollDeltaY/X` 判定方向并调用 `onScrollStart()`。

### 关于「内容哈希残留」的核实结论

`EventDispatcher.kt:155`（焦点去重）与 `ReaderAccessibilityService.kt:580`（滚动去重）
使用了 `node.hashCode()`。核实天坦源码后确认**这两处是正确的**：

1. **焦点去重**：天坦 `AccessibilityEventDispatcher.isDuplicateFocus()` 用的就是
   `source.hashCode()`（内容哈希）。语义是「同一个节点重复收到焦点事件」，内容哈希正确。

2. **滚动去重**：天坦 `M6/r` 的内部类 `NodeIdentifier` 用
   `wVar.hashCode() + wVar.U()`（内容哈希 + 窗口 ID）。本项目实现一致。

**结论**：不是 bug。上一轮修复的是 `speakNode`/`speakHover` 的**朗读去重**，
那两处的语义是「是不是同一个节点」，必须用身份，已改对。

### 关于「空 catch 块」的核实结论

9 处空 catch 全部位于 `shutdown()` / `onDestroy()` 路径，
用于「逐个关闭资源，任一失败不影响其余」。这是合理的防御性写法，
**但有改进空间**：加日志便于排查，否则关闭失败会静默。

建议（未实施，留待后续）：把空 catch 改为记录 warn 级别日志。

## 给用户的验证清单（按风险排序，一次装机验完）

### 必须验（坏了等于功能不存在）

**① 粒度导航**（#1 + #9，两者要一起验）
- 切到「按字」导航 → 按下一个字 → **应只念一个字**，不是整段
- 切到「按字词」→ 应只念一个词
- 这是 P0-2 + BUG-1 的联合验收；BUG-1 若没修，会念整段

**② 跨窗口导航**（#2）
- 打开一个弹窗 → 按「窗口导航」→ 应能走进去
- 再按 → 应能走出来

**③ 输入法上屏**（#6）
- 调出输入法 → 双击候选词 → **应能上屏**
- 注意：当前**没有 AIDL 入口**，只能验「降级的节点点击路径」
  是否生效；官方 `commitText` 路径需要自家输入法配合才能验

### 应该验（坏了影响体验）

**④ 滚动定位**（#4）
- 长列表里切到「跳到顶部」→ 按导航 → 应直接到顶
- 「跳到底部」用 `Integer.MAX_VALUE` 让容器 clamp，**不同 App 行为可能不同**

**⑤ 网页元素导航**（#5）
- 浏览器里切到「链接」→ 导航 → 应能按 HTML 语义跳
- 切到「链接」时，语音应念「**网页链接**」而不是「链接」

**⑥ 窗口几何分类**（#7）
- 遍历应用内容时，**不应**滑到状态栏的时间/电量上
- 这条依赖几何容差（5px），HyperOS 的实际尺寸可能不同于我假设的

### 顺带验（低风险）

**⑦ 垂直遍历**（#3）
**⑧ 进度播报**（#8）— 调音量时听是否念「百分之XX」

## 第九轮更新：变异测试（检验测试本身是否有效）

按审查报告「建议 8」，对实现**故意注入错误**，确认测试会失败。
测试不失败 = 无效测试 = 假的安全感。

### 结果

| 变异 | 结果 |
|---|---|
| 导航码取值函数改回 `typeCode` | ✅ 2 条失败 |
| 粒度切片放宽长度校验 | ✅ 4 条失败 |
| 窗口容差取消 | ✅ 4 条失败 |
| 状态栏高度比例 5→2 | ✅ 3 条失败 |
| 进度越界夹紧改错 | ✅ 4 条失败 |
| 音高指数分母 50→100 | ✅ 3 条失败 |
| 导航标签「网页链接」退回通用 | ✅ 4 条失败 |
| **输入法 API 门槛 33→26** | ❌ **逃逸** → 已修 |
| **滚动去重判定失效** | ❌ **逃逸** → 已修 |

### 两处逃逸的共同形态

**逻辑内联在依赖 Android 对象的方法里 → JVM 构造不出该对象
→ 测试只能测到外围的空值检查，核心判定零覆盖。**

- 输入法：测试全传 `null` service，而 null 检查在版本检查**之前**短路
- 滚动去重：判定在 `handleScroll(event)` 里，而
  `AccessibilityEvent.obtain()` 在 JVM 返回 null

### 统一修法：把判定抽成纯函数

| 抽出 | 从 | 补测试 |
|---|---|---|
| `ScrollDedup.isDuplicate()` | `handleScroll(event)` | 8 条 |
| `NavigationStore.resolve()` | `load(context)` | 3 组 |
| `ImeTextCommitter.isApiSupported()` | 内联版本比较 | 2 条 |

抽 `ScrollDedup` 时还加固了一处真实缺陷：
「两个 key 都取不到」原来会判为重复 → 无 source 的滚动事件
（系统合成事件）被**全部吞掉**，用户滑半天没声音。
现改为放行 —— 宁可重复播报，也不静默丢失。

### 结论

测试数 525 → 539。重点不在数量，而在**找出了三条
「看起来有测试、实际测不到」的盲区**。

## S1 的详细说明（本轮）

### 为什么测试测不到核心场景

JVM 单测里 `AccessibilityNodeInfo` 是**空壳**：
`getChild()` / `getParent()` / `getBoundsInScreen()` 全部返回默认值。
**构造不出「会被 RecyclerView 回收的树」** ——
而这恰恰是 S1 要解决的核心场景。

所以本轮回合只测了「纯计算部分」（评分、权重、边界），
**真正的验收必须真机**。

### 真机验证清单（S1）

**怎么验**：
1. 打开微信 → 进入一个**长列表**（如联系人列表）
2. 用读屏滑到**列表中段**某个联系人（记下名字）
3. **息屏，再亮屏**
4. **预期**：焦点回到那个联系人
5. **失败表现**：焦点跳到列表顶部（修复前的行为）

**再验一次跨 App**：
1. 在 App A 里滑到某处
2. 切到 App B，再切回 App A
3. **预期**：焦点回到原位置附近

**还要验滚动回收**：
1. 长列表里滑到中段某处
2. 快速大幅滑动（触发 RecyclerView 回收）
3. 滑回原处
4. **预期**：焦点不错位到相邻项

### 失败时的判断依据

日志里会有：
- `恢复焦点：按路径找回成功` → 路径恢复生效
- `恢复焦点：路径未命中 → 取第一个` → 走了兜底（说明路径没匹配上）
- `恢复焦点：无路径记录 → 取第一个` → 采集环节没生效

**这三条日志能把「哪一环坏了」定位到具体位置** ——
这是本轮特意加的，因为 S1 的失败模式靠肉眼看不出来。

## A4 连续朗读的真机验证清单（本轮新增）

**测不到什么**：朗读是否真的连续（自动推进下一项）、
TTS 完成回调时序、估算时长是否贴合真人语速。

### 怎么验

**① 基本连续朗读**
1. 打开任意长列表（如设置页）
2. 焦点停在某一项
3. **3 指三击**（原绑「屏幕识别」，该功能未实现故改绑）
4. **预期**：自动逐项朗读下去，无需滑动
5. **失败表现**：只读一项就停 / 完全没反应

**② 打断**
1. 朗读进行中，**轻点屏幕** → 预期立即停止
2. 朗读进行中，**长按** → 预期立即停止
3. 朗读进行中，**触摸探索**（拖动手指）→ 预期立即停止

**③ 进度条豁免**
1. 在有进度条的页面（如播放器）启动连续朗读
2. **预期**：进度条自动更新**不会**打断朗读
3. **失败表现**：每走一格就断一次

**④ 结束**
1. 一直读到页面末尾
2. **预期**：播完成音 + 自动停止

**⑤ 估算时长是否合理**
- 若「长文本没读完就跳走」→ 调大 `PER_CHAR_MS`
- 若「短文本读完干等」→ 调小 `BASE_DELAY_MS`

### 失败判断依据（日志）

- `连续朗读：被事件打断（type=X）` → 打断生效，可据 type 判断是哪个事件
- `连续朗读：已读到末尾` → 正常结束
- `连续朗读：推进异常 xxx` → 推进出错

## 【重要】本轮发现的崩溃缺陷（已修，需真机复验）

**`gestureActions` 声明为 `lateinit` 却从未初始化**，
而它在 3 处被使用：
- `isMediaPlaying = { gestureActions.isMediaActive() }`
- `onMappedAction = { gestureActions.handleMappedGesture(id) }`
- `handleMediaGesture → gestureActions.handleMappedGesture(id)`

**首次手势就会抛 `UninitializedPropertyAccessException`，
整个无障碍服务崩溃 —— 用户彻底失去辅助。**

已实例化并注入。**真机复验**：按任意映射手势（如双指上滑滚动），
服务不应崩溃。

## A5 TTS 补全的真机验证清单（本轮新增）

**测不到什么**：系统设置变更是否真的送达（ContentObserver 是否触发）、
唤醒锁是否真的阻止休眠 —— 都需真机。

### 怎么验

**① 系统设置改语速**
1. 打开 设置 → 无障碍 → 文字转语音（或 TTS 输出）
2. 把语速从正常调到最快
3. **预期**：白茶立刻用新语速朗读，**无需重启服务**
4. **失败表现**：语速不变（说明 ContentObserver 没生效）

**② 系统设置改引擎**
1. 同上路径，换一个 TTS 引擎（如换成讯飞/Google）
2. **预期**：白茶切换到新引擎
3. **失败表现**：仍用旧引擎

**③ 唤醒锁**
1. 启动连续朗读（3 指三击），或读一段长文本
2. **预期**：朗读期间屏幕不自动熄灭
3. **预期**：读完最后一句后屏幕才熄灭（`ON_AFTER_RELEASE` 的延迟效果）
4. **失败表现**：读到一半熄屏 / 读完后屏幕立即黑（无延迟）

**④ 电池（引用计数正确性）**
1. 反复触发朗读 20 次左右
2. 检查 设置 → 电池 → 白茶读屏 的耗电
3. **失败表现**：待机耗电异常（说明唤醒锁未释放）
   —— 这是引用计数写错的典型症状

### 失败判断依据（日志）
- `TTS 设置监听：已注册` → 注册成功
- `TTS 设置变更：语速 → X` → 观察生效
- `唤醒锁：已获取` / `唤醒锁：已释放` → 计数正确
- `唤醒锁：释放失败 xxx` → 计数异常

## S2. `findFirstFocus` 策略起点修复的真机验证清单（第八轮）

**修了什么**：`findFirstFocus(FORWARD)` 原本有一条「root 可聚焦就直接返回 root」
的快路径（`FocusSearch.kt`），绕过了 `traversal.start()`。依据 TalkBack
`TraversalStrategyUtils.java:396~410` 与天坦 `d7/C1421v.java:159~180`
（两个独立来源），起点**必须**来自策略。

**单测证据**（修复前实测失败）：
- `expected:<1> but was:<2>`（返回 root 而非策略起点）
- `expected:<1> but was:<0>`（`start()` 被调用 0 次）

**真机可见的差异在哪**：只有「策略起点 ≠ root」时才会表现出来。
白茶的 `DefaultTraversalStrategy.start(root, NEXT)` 返回 root 自身
（对齐天坦 `C1418s.c()`），所以**默认模式下这条修复不改变行为** ——
真正受影响的是起点与 root 不同的策略。

### 怎么验

**① 恢复焦点到页面第一个元素**
1. 打开任意有列表的 App（设置 / 微信会话列表）
2. 焦点滑到中间某处
3. 用「恢复焦点」相关手势（或让窗口重新获得焦点）
4. **预期**：焦点落在**第一个可操作项**上，读屏念出该项内容
5. **失败表现**：焦点停在列表**容器**上 —— 用户听到「列表」/「网格」
   而不是列表里第一个条目的内容。**这就是本条修复要消除的症状。**

**② 列表遍历模式下的起点**
1. 切到「列表遍历」导航（`NavigationMode.LIST_TRAVERSAL`）
2. 焦点清空后重新进入某列表页
3. **预期**：焦点落在列表**第一项**，不是容器
4. **失败表现**：念出容器本身

### 已知限制（重要，写清楚）
`findFirstFocus` 只在两处被调用：`ReaderAccessibilityService` 的
「恢复焦点」路径（`direction = FORWARD`）与 `WindowTraversal`。
**左右滑动找下一个焦点不走这条路径**（它走 `FocusManager.searchFocus`）。
所以**不要**把「左右滑动仍不正常」误判成这条修复没生效 —— 那是另一个问题。
本次修复的直接症状是「焦点停在容器上」。

## S4. ⚠️ `traversalType` 架构问题的真机优先级（最高，尚未修）

**问题**：白茶把天坦的 `i10` 当成「遍历器选择器」用

但天坦 `d7/C1421v.java:254~268` 的 `h()` **只认 2 和 8**，
`i10` 的主用途是 `t(i10)`（`:1950~1978`）的**过滤器**选择器。
天坦的「列表遍历」= 遍历顺序不变 + 过滤器跳过非列表项。

**已实测坐实的一条后果**：`ListTraversalStrategy.getFocusableChildren()`
只下钻一层，「可聚焦分组包着可聚焦项」的结构里，项会被整体跳过
（`TraversalStrategyTreeTest.listTraversal_start_misses_deep_nested_items`）；
同样结构下 `DefaultTraversalStrategy` **能**到达（同文件另一条测试）。

### 怎么验（请在真机上试这三个模式，把表现告诉我就行）

对每个模式，记录「是否可正常逐项浏览、有没有漏项、起点对不对」：

1. **列表遍历**（`LIST_TRAVERSAL`）
   - 找一个「分组标题 + 组内若干项」的界面（设置页、微信会话列表）
   - **预期**：能逐项浏览到**组内的项**
   - **失败表现**：只停在分组标题上，组内的项完全浏览不到

2. **行列遍历**（`ROW_AND_COLUMN_TRAVERSAL`）
   - 找一个网格界面（桌面、应用商店、图片网格）
   - **预期**：上下左右都能走，不跳格
   - **失败表现**：某一方向走不动 / 顺序错乱

3. **垂直遍历**（`VERTICAL_TRAVERSAL`）

   - **预期**：只按垂直方向推进
   - **失败表现**：混进了水平方向的元素

**为什么先问不先改**：这是架构级改动（要把 `traversalType` 拆成

若三个模式真机上表现正常，说明「用策略实现过滤」这条路结果等价，

## 本轮验证方式的重要改进（第十四轮）

**「抽取纯算法」让测试从「能用」变成「能信」。**

此前 `SpatialTraversal` 把 `isCandidate`/`beamBeats`/`weightedDistance`
等**纯几何函数**写成 private 实例方法，要测它们必须先构造真节点树。
后果：这些算法**从未被逐条断言过** ——
第十四轮的负坐标中心公式 bug 就是这样活下来的。

抽取为 `SpatialGeometry`（入参 `Bounds`，纯 JVM 类型）后，
21 条算法断言可直接写。

**同类已抽取**：
| 原位置 | 抽到 | 收益 |
|---|---|---|
| `WindowTraversal` 的跨窗口下标算法 | `WindowOrdering` | 绕开 `AccessibilityWindowInfo` 是 **final 类** |
| `SpatialTraversal` 的几何判定 | `SpatialGeometry` | 绕开节点替身需求 |
| `NodeOrderComparator` 的排序判定 | 直接测（FakeNode） | 绕开字段空壳 |

**通用判据**：一个函数如果**只依赖值类型**（Int/Bounds/数据类），
却被写在需要 Android 对象的类里作为 private，
它大概率就是「测不到但很重要」的那种 —— **应当抽出来**。

## S11. 日志时间戳（第二十四轮）

**修了什么**：`ReaderLog.timeFormat` 由 static 单例改为 `ThreadLocal`。

### 怎么验

这条**不需要你在真机上专门试** —— 它属于「日志本身是否可信」的基础设施。
但下次排障时请注意：

**验证点：日志里的时间戳是否单调递增**
1. 复现任意问题后，导出日志（App 内日志面板）
2. 看时间戳列是否**顺序递增**（`MM-dd HH:mm:ss.SSS`）
3. **失败表现**（修复前的症状）：时间戳**大范围乱跳**
   （例如前后两条相差几分钟，或出现未来的时间）
   —— 这说明多线程格式化仍在互相踩

**为什么重要**：排障时正是靠时间戳判断「谁先谁后」来还原因果。
时间戳不可信会**推出完全相反的结论** ——
这正是目标纪律③「不许被日志带偏」的前提。

**实测数据**：16 线程 × 20000 次、不同时间值 ——
共享实例错乱 **224015** 次，每线程一实例错乱 **0** 次。

## ★ 本轮的一条方法论收获（值得记住）

**并发缺陷的复现，必须让共享状态被写入不同的值。**

我第一版测试用**同一个固定时间值**并发格式化 → 错乱 0 次、异常 0 次，
测试失败（没能复现）。原因：内部 `Calendar` 被反复写入**相同的值**，
线程互相踩也踩不出差异。

改成**不同时间值** + 提高并发后立即复现（22 万次错乱）。

这条对将来写并发测试都适用：
> 用不变的值去压测共享可变状态，等于什么都没测。

## S12. TTS 漏读内容（第二十六轮）

**修了什么**：TTS 回调忽略 `utteranceId`，陈旧回调会把**新项**误判为完成。
已加两道防线（回调侧识别 + 主线程复核）。

### 怎么验

**① 快速连续滑动（最直接）**
1. 打开一个有长列表的 App（设置页 / 微信会话列表）
2. **快速地**连续左右滑动十几次
3. **预期**：每一次滑动都念出对应内容，**一条不漏**
4. **失败表现**（修复前的症状）：**偶尔漏掉一条** ——
   明明滑了一下，却没听到任何内容，或直接跳到下下个元素。
   注意：这种现象**日志上看不出异常**（显示为正常完成），
   所以不能靠日志判断，只能靠"少听了一条"的主观感受。

**② 切换语音引擎后立刻滑动**
1. 进「语音设置」换一个 TTS 引擎
2. 返回后**立刻**快速滑动
3. **预期**：正常播报
4. **失败表现**：换引擎后的**第一条**内容被跳过

**③ 朗读长文本时快速打断**
1. 让读屏念一段长文本
2. 念到一半时快速滑到下一个元素（触发 QUEUE_FLUSH）
3. **预期**：立刻念新元素的内容
4. **失败表现**：新元素**完全没被念**，直接停住

**看哪行日志**（tag `SpeechEngine`）：修复后出现陈旧回调时会有
- `忽略陈旧的 onDone: baicha_N（当前=baicha_M）`
- `忽略陈旧的 onError: ...`
- `主线程复核：完成回调属于项 N，但当前是项 M → 忽略`

若第 ① 步仍漏读，但日志里**没有**上面任何一条 →
说明漏读不是这个原因，需另找（可能是队列容量或事件被丢）。

### 已知限制（有意为之，不是缺陷）
`callbackId` 为 **null 时放行**，不拦截。
部分旧版/第三方 TTS 引擎不传 utteranceId；
若一律拦掉会导致**完全不出声**，比偶尔漏读严重得多。
故策略是「只拦明确不匹配的」。

## S13. 焦点音效判定（第二十九·三十轮）

**修了什么**：`isActionable` 有两处**逐字相同的错误拷贝**
（`AccessibilityEventHandler` + `ReaderAccessibilityService`），
现已统一到 `ShouldFocusNode.isActionableLike()`。

两处偏差：
- **A**：动作 ID 写成 `131072`（那是**事件**常量），天坦用 `1024`
  （`ACTION_NEXT_HTML_ELEMENT`，见 `o0/NodeInfo.java:477`）——恒不匹配
- **B**：只查 `actionList`，漏了 `getActions()` **位掩码**路径

### 怎么验

**① 焦点音效区分（本条修复的直接场景）**
1. 打开任意界面，用左右滑动在**可点击按钮**与**纯文本**之间来回移动
2. **预期**：停在可点击元素上时听到/感觉到**「可点击」提示音 + 震动**；
   停在纯文本上时是**普通文本提示音**
3. **失败表现**（修复前）：可点击元素也给出「普通文本」的提示音 ——
   两者听不出区别

**为什么这条对你重要**：你靠音效区分「这里能点」和「这里只是文字」。
判定恒偏「不可操作」= **拿掉了你的一个判断依据**。

**② 滑不到的元素（偏差 B 的直接场景）**
1. 找到某个你能看到但读屏**滑不到**的按钮（如果有的话）
2. **预期**：能滑到
3. **失败表现**：某些按钮怎么滑都跳过 —— 那类节点的动作只写在
   `getActions()` 位掩码里、没进 `actionList`，修复前会被判「不可操作」

### 无日志
本修复无专门日志。第 ① 步是纯听觉判断。

## 二、性能设计要点

| 机制 | 位置 | 说明 |
|---|---|---|
| **环形缓冲事件队列** | `EventQueue` | 预分配数组 + head/tail 双指针，稳态零 GC |
| **三代节点缓存** | `NodeCache` | 子节点列表 / 可聚焦判定 / 合成文本 |
| **O(1) 整体失效** | `NodeCache` | 代数自增代替逐个 clear |
| **展开式遍历** | `CachedTraversalStrategy` | 一次性展开成数组，后续 O(1) 索引查找 |
| **有效边界缓存** | `NodeBoundsCalculator` | 避免容器边界误判（对 TalkBack 加了跨调用缓存）|
| **B 通道懒创建** | `SpeechEngine` | 多数用户不触发打断播报，省一个 TTS 实例 |
| **正则预编译** | `ReadReplacement` | 添加时编译 Pattern，不每次编译 |
| **快路径零分配** | `ReadReplacement` / `TextDiff` | `contains()` 探路，无匹配直接返回原对象 |
| **类加载缓存** | `ClassLoadingCache` | 角色判定热路径不再反复 `Class.forName`（拿 ClassLoader 锁）|

## 三、缓存失效策略（关键正确性保障）

| 触发时机 | 动作 |
|---|---|
| 窗口状态变化（32） | `nodeCache.invalidateAll()` + `NodeBoundsCalculator.clear()` |
| 窗口集合变化（4194304） | 同上 |
| 内容变化（2048） | 同上 |
| 滚动（4096） | `nodeCache.invalidateFocus()` + `NodeBoundsCalculator.clear()` |
| 横竖屏切换 | `NodeOrderComparator.initFromContext()` + 全清 |
| 粒度/导航切换 | `nodeCache.invalidateAll()` |

**注意**：滚动时只失效「判定 + 文本 + 边界」，**保留子节点列表缓存**
（滚动时树结构不变，只有可见性/位置变化）。

## 五、工程约定

### 节点比较必须用身份
`AccessibilityNodeInfo` 重写了 `equals`/`hashCode`（内容语义），
但读屏场景大多需要**对象身份**。约定：

- 集合去重、遍历防环、节点对比 → **必须** `===` / `System.identityHashCode()`
- 例外：焦点事件去重（`EventDispatcher.isDuplicateFocus`）与
  滚动去重（`hashCode + windowId`）**故意用内容哈希**，对齐天坦语义

### 缓存必须能失效
新增任何缓存都要回答：**什么时候失效？**
并把失效调用挂到「窗口变化 / 内容变化 / 滚动 / 配置变化」四个钩子上。

### 关闭路径不静默
组件关闭用 `shutdownSafely(name) { ... }`，失败记录日志。

### 不调用 recycle
天坦 `o0.w.x0()` 是空实现，主动禁用了节点回收。本项目同样**不调用** `recycle()`。

## 六、缓存失效的工程化机制

**问题**：缓存有 9 处、分散在 7 个类里，每处都要记得在正确时机失效。
这是靠记忆维持的约定 —— `TatansTraversal` 索引缓存的 bug 就是这么来的。

**方案**：`CacheRegistry` —— 所有缓存向它登记失效回调并声明级别，
服务只调用一次 `invalidate(level)`，全部自动处理。

```kotlin
// 新增缓存的正确姿势（而不是"记得在服务里加一行 clear()"）
CacheRegistry.register(CacheRegistry.Level.WINDOW, "myCache") { myCache.clear() }
```

### 失效级别与包含关系

```
CONFIG ⊇ WINDOW ⊇ CONTENT ⊇ SCROLL
```

| 级别 | 触发时机 | 语义 |
|---|---|---|
| `CONFIG` | 横竖屏切换 | 屏幕尺寸变 → 最彻底 |
| `WINDOW` | 窗口/内容变化 | 树结构变 |
| `CONTENT` | 导航/粒度切换 | 过滤器变 |
| `SCROLL` | 滚动 | 只有可见性/位置变，**结构没变** |

**SCROLL 是唯一的"轻量"级别** —— 只清判定/文本/边界，
保留子节点列表等重缓存（滚动时树结构不变）。

## 七、缓存体系清单

| 缓存 | 位置 | 键语义 | 失效方式 |
|---|---|---|---|
| 子节点列表 | `NodeCache.childrenCache` | 身份 | 代数自增（window/content） |
| 可聚焦判定 | `NodeCache.focusCache` | 身份 | 代数自增 / `invalidateFocus()` |
| 合成文本 | `NodeCache.textCache` | 身份 | 代数自增 / `invalidateFocus()` |
| 遍历索引 | `TatansTraversal.cache*` | **内容哈希**（自失效）+ 代数 | 内容变化自动；代数双保险 |
| 有效边界 | `NodeBoundsCalculator.boundsMap` | 身份 | `clear()` |
| 类对象 | `ClassLoadingCache.classCache` | 类名字符串 | 容量淘汰 |
| 继承关系 | `ClassLoadingCache.assignCache` | `子 父` | 容量淘汰 |

**审计要点**：新增缓存必须回答「键用什么语义」与「何时失效」。
- 身份键的缓存 **必须** 向 `CacheRegistry` 登记

## 八、滚动焦点恢复（本轮新增）

**问题**：自动滚动是「先滚动、再聚焦」的两步操作，有多个失败点：
① App 不响应滚动 ② 目标未出现 ③ 滚动后节点被回收 ④ 重试死循环。

**新增 `ScrollFocusRecovery.kt`**（171 行），对应天坦 `M6/h` 内部类 `c` + `a`：

| 常量/能力 | 天坦 | 本项目 |
|---|---|---|
| 重试上限 | `i9 > 100` | `MAX_ATTEMPT = 100` ✅ |
| 重试间隔 | 25ms | `RETRY_DELAY_MS = 25` ✅ |
| 慢速延迟 | 500ms（targetType==2）| `SLOW_RETRY_DELAY_MS = 500` ✅ |
| 聚焦动作码 | `0→6, 1→8, 其他→10` | 同 ✅ |
| `boundsChanged` 判定 | 有 | `hasBoundsChanged()` ✅ |
| 失败回调 | `onAutoScrollFailed()` | `ScrollRecoveryCallback` ✅ |
| 假定成功 | `assumeScrollSuccess()` | 同 ✅ |

**接线**：滚动失败 → 服务回调 → **兜底跨窗口导航**（与 P0-1 联动）

## 九、屏幕状态恢复（本轮新增）

**这是焦点系统「恢复层」的第三条路径**（前两条：跨窗口导航、滚动恢复）。

| 路径 | 触发 | 对应 |
|---|---|---|
| 跨窗口导航 | 用户滑动到窗口边界 | 天坦 `M6/h.F()` |
| 滚动后恢复 | 自动滚动失败 | 天坦 `M6/h.a` |
| **屏幕状态恢复** | **息屏亮屏 / 切应用 / 弹窗关闭 / 旋转** | **TalkBack `FocusProcessorForScreenStateChange`** |

**新增 `ScreenStateRecovery.kt`**（281 行），三个守卫条件：

| 守卫 | 条件 | 结果 |
|---|---|---|
| ① | 无活动窗口 | `FAIL_NO_ACTIVE_WINDOW(-3)` |
| ② | **用户在切换期间已操作** | `FAIL_HAS_INTERACTION(-2)` |
| ③ | 窗口内已有有效焦点 | `FAIL_HAS_VALID_FOCUS(-1)` |
| — | 全部通过 | `SUCCESS(1)` → 恢复焦点 |

**守卫 ② 是防抢焦点的关键**：窗口切换是异步的，用户可能已经等不及开始滑动。
此时若"恢复焦点"会跳到用户不想要的位置。TalkBack 用
「切换开始时间 vs 用户最近操作时间 + 来源判定」避免这个竞态。

**延迟机制**：切换耗时 < 500ms（`WINDOW_CHANGE_DELAY_MS`）时延迟执行，
因为「会先播报窗口标题，用户感觉不到延迟」，同时给窗口切换留时间。

## 十一、焦点监控（本轮新增，P2 完成）

**新增 `FocusMonitor.kt`**（247 行），对应 TalkBack `AccessibilityFocusMonitor`（234 行）。

### 多级回退链

原来的 `FocusManager.getFocused()` 只做「取当前焦点」，TalkBack 把它做成了决策：

| 级别 | 条件 | 说明 |
|---|---|---|
| ① | 无障碍焦点存在且可见 | 常规路径 |
| ② | 退回输入焦点 | 要求可编辑（`requireEditable`）|
| ③ | 退回历史最后的编辑框 | **要求输入法窗口在屏** |
| ④ | 都没有 | null |

### 第 ③ 步的价值

WebView / 自绘编辑框的输入焦点可能是**虚拟视图**，
`findFocus(FOCUS_INPUT)` 取不到东西。此时用「历史编辑框 + 输入法在屏」
双条件兜底，能恢复出正确的编辑框焦点 —— 否则**在网页里输入时焦点会丢**。

TalkBack 原注释：
> "If we can't find the focused node but the keyboard is showing, return
>  the last editable. This will occur if the input-focused view is actually
>  a virtual view (e.g. in WebViews)."

**接线**：`FocusManager.monitor` 注入；设焦点成功时 `recordEditableFocus()`；
窗口变化时 `onWindowChanged()` 清理历史。

## 十二、可滚动容器查找（本轮新增，P1-3 完成）

**新增 `ScrollableNodeFinder.kt`**（280 行），对应 TalkBack
`searchScrollableNodeFromBfs()`。

### 两种策略，各有用途

| 策略 | 速度 | 适用 |
|---|---|---|
| `findScrollableAncestor()` | 快 | 已在容器内（常见场景）|
| `search()`（BFS）| 慢 | **嵌套滚动** |

### BFS 解决什么问题

嵌套滚动场景：
```
外层纵向列表
  └─ 内层横向列表   ← 从内层项向上找会选中它
```
用户想滚整个页面（外层），却滚动了内层横向列表。

TalkBack 用 **BFS 从根往下找**，再配合「最大滚动容器」选择：

1. BFS 找第一个可滚动节点（保证只滚「最外层」）
2. 找**面积最大**的可滚动节点
3. **Pager 降权**：只有屏上无其他可滚动节点时才用 Pager

TalkBack 原注释：
> "…even though the pager is bigger than the scroll view, we may prefer to
>  select the scroll view since the content user interested should be inside it."

### 接线

`ensureVisible()` 改为**两级策略**：先向上找（快），找不到再 BFS 兜底。

# 测试基础设施限制 —— Rect 在 JVM 单测中是空壳

> 发现时间：2026-10-02（第七轮）
> 影响范围：所有依赖 `android.graphics.Rect` 的算法测试

## 一、发现过程

实现 `SpatialTraversal` 的 TalkBack 算法后，我写了 20 个几何测试，
按 TalkBack 的 `isCandidate` / `beamBeats` / `weightedDistance` 逻辑
手工验算全部通过预期，但**运行时全部失败**。

逐步排查：

```
① 反射签名检查  → isCandidate(Rect, Rect, int)，参数正确
② 方向常量检查  → TraversalDirection.UP = 5，正确
③ 手工求值检查  → (b>db or t>=db) && (t>dt) = true，与实现一致
④ 打印 Rect 实际值 → ★ src: l=0 t=0 r=0 b=0（传入的是 0,100,100,200）
```

## 二、根因

**`android.graphics.Rect` 在 JVM 单元测试中是空壳实现。**

即使项目已开启 `testOptions.unitTests.isReturnDefaultValues = true`：

| 操作 | 期望 | 实际 |
|---|---|---|
| `Rect(10, 20, 30, 40).left` | 10 | **0** |
| `Rect(10, 20, 30, 40).width()` | 20 | **0** |
| `rect.set(1, 2, 3, 4)` | 生效 | **无效果** |
| `rect.isEmpty` | false | false（凑巧对） |

也就是说：**Rect 不保存任何数据**，所有几何运算都在全 0 上执行。

`isReturnDefaultValues = true` 让未 mock 的方法返回默认值而不是抛异常
—— 这对 `Log`/`SystemClock` 是便利，但对 `Rect` 这类**数据容器**是陷阱：
它让测试**看起来能跑**（不抛异常），但结果毫无意义。

## 三、影响

| 模块 | 是否受影响 | 说明 |
|---|---|---|
| `SpatialTraversal` | ⚠️ 严重 | 核心全是 Rect 几何算法，无法单测 |
| `NodeBoundsCalculator` | ⚠️ 严重 | 边界并集/裁剪全是 Rect 运算 |
| `NodeOrderComparator` | ⚠️ 部分 | 排序用 Rect 比较 |
| `TraversalDirection` | ✅ 不受影响 | 纯 int 常量 |
| `FocusSearch` | ✅ 不受影响 | 纯集合逻辑 |
| `EventQueue` / `CacheRegistry` / `TextDiff` / `ReadReplacement` | ✅ 不受影响 | 不依赖 Rect |

## 四、处理决策

**当前选择：把几何算法交给真机验证，测试只覆盖结构性契约。**

理由：
1. 引入 Robolectric 成本较高（需配置、拖慢构建、版本兼容）
2. 把算法抽到不依赖 `android.graphics` 的纯 JVM 层需要重构
3. 几何导航的最终判据是「真机上选得对不对」，单测价值有限

**已做**：
- 删除 20 个虚假的几何测试（它们在全 0 数据上"通过"毫无意义）
- 替换为 `SpatialTraversalStructureTest`：只测枚举/常量/空值安全
- 在测试类注释里**明确记录这个限制**，避免后来者重复踩坑

## 五、后续可选方案

若将来需要真正的几何测试，可考虑：

**方案 A：Robolectric**
```kotlin
testImplementation("org.robolectric:robolectric:4.11.1")
// @RunWith(RobolectricTestRunner::class)
```
优点：直接可用真实 Rect；缺点：构建变慢、需管理版本。

**方案 B：抽象几何层**
把算法参数从 `android.graphics.Rect` 换成自定义的 `Bounds` 数据类：
```kotlin
data class Bounds(val left: Int, val top: Int, val right: Int, val bottom: Int)
```
优点：纯 JVM 可测、零依赖；缺点：需要在调用处做一次转换（有性能成本）。

**方案 C：真机单元测试**
用 `androidTest`（instrumented test）跑几何断言。
优点：环境真实；缺点：需要设备/模拟器。

## 六、已解决（方案 B 实施）

**2026-10-02 第八轮：已采用方案 B（抽象几何层）并落地。**

### 做法

新增 `Bounds.kt`（238 行）—— 不依赖 `android.graphics` 的纯几何类型：

```kotlin
data class Bounds(val left: Int, val top: Int, val right: Int, val bottom: Int) {
    constructor(rect: Rect) : this(rect.left, rect.top, rect.right, rect.bottom)
    fun toRect(out: Rect) { out.set(left, top, right, bottom) }
    // 纯几何运算：contains / intersects / intersectWith / unionWith / inset / offset ...
}
```

配套 `BoundsAccumulator`（子节点并集累加器，对应天坦的 minTop/minLeft/maxRight/maxBottom）。

### 改造范围（最小侵入）

| 模块 | 改动 |
|---|---|
| `SpatialTraversal` | 9 个算法方法的参数 `Rect` → `Bounds`；`findFocusInDirection` 内部改用 Bounds 流程；新增 `resolveBounds()` 作为唯一转换边界 |
| `NodeBoundsCalculator` | 抽出 `clampChildBounds(own, childBounds)` 纯函数；`fetchBound` 只负责 Android 数据采集 |
| `NodeOrderComparator` | 暂未改（41 处 Rect，收益/风险比待评估）|

### 效果

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 空间算法可测 | ❌ 20 个测试全是虚假通过 | ✅ **20 个真实通过** |
| 有效边界可测 | ❌ 无法测 | ✅ 新增 6 个测试 |
| 几何基础类型可测 | — | ✅ 新增 22 个测试 |

**测试总数：251 → 305**（净增 54 个真实测试）

### 验证方式

改造后重跑上一轮那 20 个几何测试 —— **全部真实通过**，
且多个测试断言了**精确数值**（如 `weightedDistance = 32500 / 45200`），
证明 Rect 空壳问题已绕过。

## 七、教训

**「测试通过」不等于「逻辑正确」** ——
如果被测代码依赖的类在测试环境中是空壳，测试会给出虚假的安全感。

判断方法：**在测试里打印被测数据**。
如果打印出的全是默认值（0 / null / ""），那么整组测试都不可信。

这条经验已加入本项目的工程约定。

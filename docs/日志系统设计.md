# 日志系统设计（v2）

> 实现时间：2026-10-02
> 起因：真机 P0「左右滑动找不到焦点」排查时，**日志本身成了障碍**
> 代码：`app/src/main/java/com/baicha/reader/core/LogCore.kt`（新增）、`ReaderLog.kt`（重构）
> 测试：`app/src/test/java/com/baicha/reader/core/LogCoreTest.kt`（31 个）、`ReaderLogTest.kt`（30 个）

---

## 一、要解决的三个问题

排查 P0 时日志的实际表现（真机抓取）：

| # | 现象 | 后果 |
|---|---|---|
| ① | 一秒内「焦点清除」64 行、「无障碍焦点」60 行、「触摸」48 行 | 排查者被刷屏带偏，**先怀疑了错误方向，浪费一整轮** |
| ② | DEBUG/INFO/WARN/ERROR 混在一起；焦点类、TTS 类、手势类混在一起 | 172 行里哪几行是关键，只能靠人眼看 |
| ③ | 日志文本被塞进 `onSaveInstanceState` 的 Bundle | 3 208 220 bytes 超 Binder 上限 → `TransactionTooLargeException` 杀进程 |

①→ **限流聚合**；②→ **分级 + 分类**；③→ **有界环形缓冲**。

## 二、两个参考实现的做法

### 2.1 TalkBack：只有「分级 + 格式化」，没有分类、没有缓冲

主实现是 `utils/src/main/java/com/google/android/libraries/accessibility/utils/log/LogUtils.java`：

| 能力 | 位置 | 做法 |
|---|---|---|
| 分级 | `LogUtils.java:45` `private static int minLogLevel = Log.ERROR;` | 单一全局门槛 |
| 关卡 | `LogUtils.java:239` `if (priority < minLogLevel) return;` | 直接照搬 `android.util.Log` 的常量（VERBOSE=2 … ERROR=6） |
| 预判 | `LogUtils.java:323-326` `shouldLog(int logLevel) { return minLogLevel <= logLevel; }` | 让调用方在**拼字符串之前**就能跳过 |
| 前缀 | `LogUtils.java:47` `logTagPrefix` | `setTagPrefix()` 让同一 App 的日志可整体 grep |
| **限流** | `LogUtils.java:67-81` `logWithLimit(tag, priority, index, limit, format, args)` | **计数式**：调用方自己传 `index`，超过 `limit` 就不再输出，第 `limit` 次显示 `"...; further messages suppressed"` |
| 参数定制 | `LogUtils.java` `ParameterCustomizer` | 让 AccessibilityEvent / NodeInfo 在日志里变成可读文本 |
| 深度缩进 | `utils/.../LogDepth.java:42-64` `logVar/logFunc/log(tag, depth, format, args)` | 用缩进表现调用层次 |

**TalkBack 没有的东西**：
- 没有分类维度。全部靠 tag 字符串 `LogUtils.d("FocusManager", ...)` 人工区分。
- **没有任何缓冲**——直接 `Log.println()` 写 logcat。`grep -rn "RingBuffer\|EventCategory"` 在整个 TalkBack 树里**零命中**。
- 因此它没有「日志撑爆内存/撑爆 Bundle」的风险，但代价是：`logcat` 缓冲区一滚，历史就没了；现场排查只能靠「出问题时把 logcat 存下来」。

### 2.2 天坦：真正的「诊断体系」——分类 + 环形缓冲 + 落盘快照

天坦把日志拆成了**两层**，这是它比 TalkBack 强一个量级的地方：

**第一层：文本日志 `y7/AbstractC4354b.java`（156 行）**

- `f42483a`（`:18`）= 全局级别门槛，`k()` 里 `:93` `if (i9 < f42483a) return;`
- **本质是 `LogUtils` 的 Kotlin 化翻版**，连 API 都对应：
  - `l()`（`:108-113`）就是 TalkBack 的 `logWithLimit`，连提示文案都一模一样：`"%s (%d); further messages suppressed"`
  - 级别→方法的映射（`:126-145` `q()`）用 `android.util.Log` 常量
- 底层**不写文件**，走腾讯 Mars Xlog（`Log.java` / `Xlog.java`，`:60` `Log.setLogImp(new Xlog())`），原生层负责压缩落盘

**第二层：诊断引擎 `net/tatans/soundback/diagnosis/`（17 个类，2814 行）**

| 类 | 行数 | 职责 |
|---|---|---|
| `EventCategory.java` | 46 | **分类枚举**：`SPEECH / WAKELOCK / OCR / NETWORK / SCREEN / GESTURE / FOCUS / SERVICE`（按子系统切） |
| `DiagnosisEvent.java` | 119 | **结构化事件**：`(timestamp, category, action, detail)`（`:17`），带 `toJson()`（`:100`） |
| `EventRingBuffer.java` | 72 | **有界环形缓冲**：`capacity` + `AtomicLong cursor`，`buffer[cursor.getAndIncrement() % capacity] = event`（`:30`）；`snapshot(n)` 取最近 n 条（`:45-57`）；`getSize()` 用 `Math.min(capacity, cursor)`（`:41-43`） |
| `DiagnosisEngine.java` | 586 | 单例门面：`EventRingBuffer(2000)`（`:152` 静态块）、`reportEvent(category, action, detail)`（`:487`）在 `enabled` 为真时入环（`:490-492`） |
| `SnapshotDumper.java` | 147 | 把环形缓冲快照写成 **JSON 文件**（`getFilesDir()/diagnosis/snapshot_<TYPE>_<时间>.json`，`:75`） |
| `CpuMonitor` / `MainThreadMonitor` / `ThreadLoopDetector` / `AudioTrackMonitor` / `WakeLockTracker` / `NetworkTracker` | — | 每个监控器在越界时触发 `dumpSnapshot(类型, 说明)` |

天坦最值得学的一点：`DiagnosisEngine.reportEvent` 把**无障碍的关键动作**（`:477-485` 里 `speech_start` / `speech_end` 由 `SpeechController.i` 回调触发）直接喂进环形缓冲，于是「日志」和「诊断」是**同一份数据**：出问题时 dump 出的快照既可以给人看，也可以作为结构化事件流被程序读回来。

### 2.3 取舍：采纳天坦的两级结构，TalkBack 的 `shouldLog` 预判

本项目规则是「A/B 取舍时优先选天坦」，这里也确实该选天坦：

| 维度 | TalkBack | 天坦 | 本项目采纳 | 理由 |
|---|---|---|---|---|
| 分级 | minLogLevel | minLogLevel | **两者一致的部分** | 无争议 |
| 分类 | ❌ 无 | ✅ `EventCategory` | **天坦** | 需求 4「只看 TTS、只看焦点导航」没有分类根本做不到 |
| 事件结构 | ❌ 纯字符串 | ✅ `DiagnosisEvent` | **天坦** | 结构化才能稳定筛选（见 §6.1） |
| 有界缓冲 | ❌ 无 | ✅ `EventRingBuffer(2000)` | **天坦** | 需求 7「不能成为崩溃源」的**唯一**解法 |
| 落盘 | logcat | Xlog + JSON 快照 | **天坦思路，改用纯 Java** | 项目已有 `ReaderLog` 写 `/sdcard/Download/baicha-reader.log`；不引 Mars Xlog（要 `.so`、要 JNI） |
| 限流 | `logWithLimit` 计数式 | 同（`l()`） | **两家都不够，自己做** | 见 §3.2 |
| 预判关卡 | ✅ `shouldLog` | ✅ 隐含在 `k()` 里 | **两家都有** | 让调用方在拼串前就能跳过 |
| 环的过滤能力 | — | 只能「取最近 n 条」 | **扩展** | 需求 4 要「按分类取」，天坦的 `snapshot(n)` 不够 |

**明确不采纳的**：
- **Mars Xlog**（天坦 `AbstractC4354b.java:60` 起）：需要 `libmarsxlog.so` + JNI，且加密落盘后**排查者不能直接 `cat`**。本项目的核心 Debug 场景是「用户把手机上的日志文件发出来，我直接读」，明文文件比什么都重要。
- **TalkBack 的纯 logcat 路线**：MIUI 过滤 `Log.d/v`（`ReaderLog.kt` 头部注释已记录），且历史会滚掉。
- **`logWithLimit` 的计数式限流**（见下节）。

## 三、新系统的设计

### 3.1 分层

```
                  ┌──────────── 写入侧（无障碍交互线程）────────────┐
ReaderLog.d/i/w/e ─┤                                                │
ReaderLog.log(…)  ─┤ → ① 级别闸门（低于门槛直接 return，不建对象）    │
ReaderLog.focus(…)-┤ → ② 分类推断（按 tag 前缀表 / 显式传入）        │
                  │ → ③ 限流聚合 ← 被聚合的行**连字符串都不生成**    │
                  │ → ④ 格式化                                        │
                  │ → ⑤ 内存缓冲（文本 500 行 + 结构化 2000 条）      │
                  │ → ⑥ 回调（日志面板）                              │
                  └────────────────────┬───────────────────────────┘
                                       │ 唯一的重活，丢给后台线程
                                       ▼
                              BaiChaLogWriter（单线程）
                                       │
                                       ▼
                     /sdcard/Download/baicha-reader.log（2 MB 轮转 .1）
```

对应天坦的两级：④⑤⑥ 相当于它的 `AbstractC4354b`（文本日志），
③⑤ 相当于它的 `DiagnosisEngine` + `EventRingBuffer`（事件总线）。

### 3.2 限流聚合的算法（核心）

**为什么 TalkBack/天坦那套计数式限流不够**

`logWithLimit(tag, priority, index, limit, ...)` 要求**调用方自己维护并传递 `index`**。这意味着：

1. 每个要限流的调用点都得自己持有一个计数器 —— 读屏里高频日志点有几十处，等于要求每处都写一遍限流逻辑；
2. 计数是**跨会话累积**的，`index > limit` 之后**永久静默**，而不是「这一秒太多了，下一条还是会出来」；
3. 无法回答「**哪个**模式在刷屏」——只能回答「总量超了」。

**本系统的做法：按 `(分类, 级别, 消息模式)` 分组的时间窗口**

| 步骤 | 说明 |
|---|---|
| **键** | `分类 \| 级别 \| 消息模式` |
| **消息模式** | 用一条正则把「会变的部分」替换成 `#`：<br>`'…'`、`"…"`、`「…」`、`(…)`、`0x…`、`-?\d+(\.\d+)?` → `#`<br>于是「无障碍焦点: 设置项 3」和「…设置项 4」是**同一个模式** |
| **窗口** | 每个键一个 `Window(startMs, count, summaryEmitted)`，窗口长 1000 ms |
| **判定** | 见下 |

```
sample(key, message, now):
    w = table[key]
    if w == null 或 now - w.startMs >= windowMs:        ← 新窗口
        输出（emit=true, count=1）
    else:
        w.count++
        if w.count >= 8 && !w.summaryEmitted:            ← 突刺：提前给一次摘要
            输出摘要（emit=true, count=当前累计）
        else:
            不输出（emit=false），仅在计数
```

三条设计规则，每条都有理由：

**① 窗口长 1 秒、每窗口至少输出一条**

稳定的 1 Hz 事件（每秒一次的心跳、每秒一次的电量播报）**不会被误合并** ——
它们本来就落在不同窗口里。只有**同一窗口内的重复**才聚合。

这比「固定 N 条抽 1 条」好在：不丢「发生了什么」，只压缩「发生了几次」。
「10:00:01 焦点清除」和「10:00:05 焦点清除」是两个不同的事实，
抽 1 条会让第二个事实消失；窗口聚合则保留两条。

**② 突刺提前给摘要（阈值 8）**

纯时间窗口在窗口**末尾**才输出，最坏情况是「刷屏开始后 1 秒内面板一片空白」。
达到 8 次就立刻先给一条摘要，**刷屏现场即时可见**；
同时该窗口内不再重复给（`summaryEmitted` 一次性置位），不会变成另一种刷屏。

阈值选 8 的理由：小于它的重复（2~7 次）多半是正常的连击/重复事件，
逐条看反而有信息量。

**③ 限流表容量 512，超限逐出最旧的**

键里含消息文本。如果调用方把节点文本拼进消息
（`"焦点落到「$text」"`），**每个节点都是新键** ——
表会随节点数无界增长，那就是用另一种方式复现「日志撑爆内存」。

512 条 × 约 200 字节 ≈ 100 KB，恒定。
逐出时**宁可少聚合也不丢日志**：逐出后该消息若再次出现，会重新输出一次
（压缩率下降，但一条都不丢）。

**效果（真机 P0 现场）**

| | 之前 | 之后 |
|---|---|---|
| 一秒内「焦点清除」 | 64 行 | 1 行 `焦点清除` + 1 行 `焦点清除 x64（最近 1000ms）` |
| 一秒内总数（三类） | 172 行 | ≤ 6 行 |

**为什么不用令牌桶**：令牌桶只能回答「太多了」，不能回答「哪个太多了」。
按模式分组聚合既限流又保留分布信息 —— 排查时能直接看出
**是焦点在抖，不是整个系统在抖**。

### 3.3 有界性（四处上限）

| 缓冲 | 上限 | 位置 |
|---|---|---|
| 文本行（面板显示） | 500 行 | `ReaderLog.MAX_MEMORY_LINES` |
| 结构化记录 | 2000 条 | `RateLimitedRingBuffer.DEFAULT_CAPACITY`（与天坦 `EventRingBuffer(2000)` 一致） |
| 限流表 | 512 项 | `LogLimiter.DEFAULT_MAX_ENTRIES` |
| 日志文件 | 2 MB，超了轮转 `.1` | `ReaderLog.MAX_FILE_SIZE` |

**绝不再进 Bundle**：`activity_main.xml` 里 `tvLog` / `scrollLog` 保持
`saveEnabled="false"`，`MainActivity.appendLogLine` 的
`MAX_LOG_CHARS` 裁剪是第二道保险。日志是瞬时内容，无需跨进程恢复。

### 3.4 不成为性能负担

热路径（`ReaderLog.log(...)` → `emit()`）只做三件事：

1. 一次时钟读取（`SystemClock.uptimeMillis()`，Android 上无锁）
2. 一次限流表查找（`ConcurrentHashMap.compute`，键级原子、不同模式互不阻塞）
3. 一次 `synchronized` 的缓冲写入（纯内存，纳秒级）

**被聚合掉的行连字符串都不生成** —— 这是最大的一笔节省：
一秒 64 条刷屏时，格式化 + 写盘 + logcat 三份开销全部省掉 63/64。

格式化成文本、写磁盘、写 logcat，全部在 `BaiChaLogWriter` 单线程上。
这条线程与无障碍交互线程不是同一条 —— 参照 `PerfCounters` 的设计原则
（「测量本身的开销必须趋近于零」）。

## 四、API 说明

### 4.1 打日志

```kotlin
ReaderLog.init(context)                        // 应用启动时调一次

// ▸ 完全向后兼容（125 处旧调用点不用改）
ReaderLog.d("FocusManager", "moveFocus NEXT")  // DEBUG + 按 tag 自动归类 FOCUS
ReaderLog.i("BaiChaReader", "服务已连接")        // INFO  + 自动归类 SYSTEM
ReaderLog.w("NodeCache", "缓存失效")             // WARN  + 自动归类 CACHE
ReaderLog.e("TTS", "init failed", throwable)   // ERROR + 自动归类 SPEECH（含栈，最多 8 帧）

// ▸ 显式指定分类（迁移期推荐，改动最小）
ReaderLog.i("BaiChaReader", "TTS 就绪", LogCategory.SPEECH)
ReaderLog.d("Whatever", "细节", LogCategory.GESTURE)

// ▸ 完整形式
ReaderLog.log(LogLevel.WARN, tag, msg, category, throwable)

// ▸ 关键路径快捷方式（结构化，见 §5）
ReaderLog.focus("下一焦点 | ✅ 通过 → 「Wi-Fi」")
ReaderLog.focusDebug("ShouldFocusNode 否决：不可见")
ReaderLog.speech("播报: 你好")
ReaderLog.gesture("手势: 单指下滑 → 下一项")
```

### 4.2 级别与开关

```kotlin
ReaderLog.minLevel = LogLevel.WARN   // 低于 WARN 的全部丢弃（在入口就丢，连分类都不推断）
ReaderLog.enabled = false            // 总开关（面板「暂停日志」）
ReaderLog.verbose = false            // 兼容旧字段，等价于 minLevel = INFO
```

### 4.3 筛选（需求 4：只看某一类）

```kotlin
// ▸ 结构化筛选（首选 —— 不解析文本，格式改动不会让它静默失效）
ReaderLog.readRecords(setOf(LogCategory.SPEECH))          // 只看 TTS
ReaderLog.readRecords(setOf(LogCategory.FOCUS), minLevel = LogLevel.WARN)
ReaderLog.renderRecords(setOf(LogCategory.FOCUS))         // 渲染成文本行

// ▸ 功能等价，性能差一个量级 —— 需要文本行时直接用这个
ReaderLog.readByCategory(LogCategory.SPEECH)              // 按分类
ReaderLog.readByLevel(LogLevel.WARN)                      // 该级别及以上
ReaderLog.readMemory()                                    // 全部（受 categoryFilter 影响）

// ▸ 面板用：设一次，readMemory() 就只返回该类的行
ReaderLog.categoryFilter = setOf(LogCategory.SPEECH)
```

**为什么过滤放在展示侧**：写入侧过滤会让「关掉 TTS 分类」同时丢掉磁盘归档，
而真机排查往往正是**事后**才想起来要看某一类。

### 4.4 导出

```kotlin
ReaderLog.export("/sdcard/Download/all.log")                       // 完整文件
ReaderLog.export(                                                   // 只导出焦点（最近 5000 行）
    "/sdcard/Download/focus.log",
    categories = setOf(LogCategory.FOCUS),
    minLevel = LogLevel.INFO,
    maxLines = 5000
)
```

### 4.5 诊断

```kotlin
ReaderLog.currentLogPath()      // 日志文件路径（面板显示用）
ReaderLog.recordCount()         // 结构化记录条数
ReaderLog.recordDroppedTotal()  // 因环形覆盖而丢失的历史条数
ReaderLog.countsByCategory()    // 每个分类各多少条
ReaderLog.pendingSuppressed()   // 此刻被压着、尚未输出的重复条数
ReaderLog.rateWindowStats()     // 「限流表 12/512 条，逐出 0，待输出 31」
ReaderLog.clear()               // 清空缓冲 + 文件（内部会一并重置限流器）
ReaderLog.clearBuffers()        // 只清缓冲，不碰文件
ReaderLog.addAggregationListener { summary -> … }   // 感知「刚才压掉了多少」
```

**为什么 `pendingSuppressed()` 要暴露**：限流把 64 条压成 1 条时，
另外 63 条是**静默丢弃**的。面板可以据此显示「此刻有 63 条同类被压着」，
让「日志变少了」不等于「日志丢了」。

## 五、结构化关键路径

需求 5 要求「一眼看出这次滑动为什么没找到焦点」。做法是**一次导航一条记录**：

```
[10:00:01.234] INFO/FOCUS/焦点 (main): ✅ 下一焦点 | 通过 → 「设置项：Wi-Fi」(btn) | 滚动拦截=通过 防抖=通过 粒度=跳过 搜索=命中(第3次)
[10:00:02.567] INFO/FOCUS/焦点 (main): ❌ 下一焦点 | 失败 ← 遍历无果（遍历了 137 个节点，全部未通过可聚焦判定） | 滚动拦截=通过 防抖=通过 粒度=跳过 搜索=失败 遍历=137节点/0命中
```

`FocusTrace`（`core/FocusTrace.kt`）是产出这种记录的 API，
它已经设计好接口（`begin/step/skip/accept/reject/end`）、
约束（最多 12 步、不持有节点、关闭时空实现零分配）和单行输出，
**本轮的日志系统为它提供了承载**：

- `FocusTrace.end()` 里的 `ReaderLog.i(TAG, …)` 现在会自动归入 `LogCategory.FOCUS`（tag = 「焦点」）
- 一次导航一行，且**抖动会被聚合**：如果焦点在抖，面板上看到的是
  「❌ 下一焦点 | 失败 ← 遍历无果… x23（最近 1000ms）」而不是 23 行几乎相同的结论
- 需要中间步骤时用 `ReaderLog.focusDebug(...)`：这些行默认也是 DEBUG，
  把 `minLevel` 调到 DEBUG 才出现，不影响正常观察

## 六、值得记录的两个工程决定

### 6.1 为什么同时保留「文本行」和「结构化记录」

`memoryLog`（`ArrayDeque<String>`，500 行）给面板显示；
`records`（`RateLimitedRingBuffer`，2000 条）给诊断筛选。

只看文本的话，筛选就必须回头解析字符串（`line.contains("/SPEECH/")`）——
一旦渲染格式变动，筛选就**静默失效**，而不报错。
项目里已经吃过「静默失效」的亏（见 `docs/静默失效审计-2026-10-02.md`），
所以这里宁可多存一份约 40 字节/条的引用。

（`categoryOfLine` / `levelOfLine` 两个文本解析函数仍然保留，
它们只用在**导出已落盘的历史文件**这条路径上 —— 那是纯文本，无法结构化。）

### 6.2 放弃跨任务合并写（一个真实踩到的坑）

最初为了省 `FileWriter` 的 open/close，写成「后一个任务把队列里
前一个任务的文本偷出来一起写」。实测出现**静默丢日志**：

```
第一条写成功 → 第二条消失 → 第三条又能成功   （严格 2 条丢 1 条）
```

根因是「偷取方把被偷任务标记成 done，但偷取方自己是否真的写出去
取决于它当时解析到的目标文件」，两者一旦不同步，被偷的那条就永远没人写。

这个 bug 危险的地方在于：它**只在连续写入时出现**，
表现正是「某几条日志莫名不见了」—— 与「日志系统整体坏掉」的表现完全一样，
会把排查者引向错误方向（正是本轮要消灭的那种情况）。

现在的做法：**每个任务只写自己持有的文本**，所有权绝不交叉。
代价是每条一次 open/close，但这条路径在 `BaiChaLogWriter` 单线程上、
不在无障碍交互线程上，与性能要求不冲突。

至于「合并」——它发生在**更前面**：同一窗口内的重复日志在进入写队列
**之前**就已被限流器聚合成一条，真正的刷屏在源头就被压掉了。

## 七、迁移指南

### 原则：**不要求一次改完**

125 处调用点、32 个文件。全部改一遍风险大且收益递减。
新系统保证**旧写法照旧可用**，迁移是**增量**的。

### 第 0 步：什么都不用做

旧的 `ReaderLog.d/i/w/e(tag, msg)` 已经能跑，并且**已经拿到大部分收益**：

- ✅ 自动分级（d→DEBUG，i→INFO，w→WARN，e→ERROR）
- ✅ 自动分类（按 tag 前缀表；`FocusManager`→FOCUS，`SpeechEngine`→SPEECH，`NodeCache`→CACHE…）
- ✅ 自动限流聚合（所有日志都过限流器，不需要调用点配合）
- ✅ 有界缓冲、异步写盘、聚合摘要

### 第 1 步：把「刷屏的那几条」显式分类（优先级最高，改动最小）

真机 P0 的刷屏来源集中在一处：`ReaderAccessibilityService.log(msg)`。
它已经改为按**消息内容**分类（`classifyServiceMessage`），
所以 `无障碍焦点: xxx`、`焦点清除`、`触摸: xxx` 这些自动落进 FOCUS / EVENT。

若你手上有真机日志发现**别的**刷屏点，照这个模式改：调用点比 tag 更知道分类。

### 第 2 步：关键路径改用快捷方式

```kotlin
// 之前
ReaderLog.i("焦点", "$mark $intent | $result | $summary")
// 之后（分类确定，走 FOCUS，不再依赖 tag 推断）
ReaderLog.focus("$mark $intent | $result | $summary")
```

优先级：焦点移动 / TTS 播报 / 手势触发 —— 这三条是排查的主干。

### 第 3 步：接上 `FocusTrace`（收益最大）

`FocusTrace` 已实现但**尚无调用点**。把它接到 `FocusManager.moveFocus()`：
一次导航 `begin()` 一次，每个判定分支 `step(name, passed)`，
结束时 `end()`。接上之后，「焦点没找到」会从
「面板上一堆无结论的行」变成「一行带全部判定结果的结论」。

### 第 4 步（可选）：把热点分类改成显式传参

`ReaderLog.d(tag, msg, LogCategory.XXX)` —— 只在 tag 推断不准时才需要。

### 别做的事

- ❌ **不要**为了「统一」批量重写所有调用点 —— 收益低、回归风险高，且旧写法没有功能缺陷
- ❌ **不要**把日志文本重新塞进 `Bundle` / `Intent` / `SharedPreferences`
- ❌ **不要**在 `ReaderLog` 的调用点里做 `if (minLevel >= …)` 之类的手工判断 —— 闸门已经在入口，且有 `LogLimiter` 兜住重复

### 测试反过来抓出的两个真 bug

这轮测试的价值不在于「证明代码能跑」，而在于**抓出了两个真实缺陷**：

1. **清空日志后同窗口内的同类日志被静默吞掉**
   限流器是有状态的（「这条模式在这个窗口里已经输出过」）。
   只清缓冲不清它，用户点「清空日志」后如果焦点还在抖，
   面板会**一直空白** —— 看起来像读屏卡死。
   修法：`clear()` / `clearBuffers()` 一并重置限流器。

2. **跨任务合并写会丢日志**（见 §6.2）
   由「连续写入后立即读文件」的断言暴露，表现为严格 2 条丢 1 条。

### 测试写法上的一个教训

最初为了让「写盘后可立即断言」，测试注入了**当前线程执行**的执行器。
这确实让测试变绿了，但它测的不是真实链路 ——
生产用的是异步单线程池。改成**保持真实异步 + 显式等待队列排空**
（`writer.queue.isEmpty() && writer.activeCount == 0`）之后，
才暴露出上面第 2 个 bug。

**注入替身让测试变绿，不等于代码是对的。**

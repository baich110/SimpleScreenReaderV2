## 二、★ 核心发现：`traversalType` 的语义被搞错了

### 2.1 天坦的真实调用链

### 2.2 `h()` 只认 3 个值，且含义与「遍历类型」无关

`d7/C1421v.java` 第 254~268 行（原样摘录）：

拆开这段嵌套三元：

| `i10` | 返回的策略 | 条件 |
|---|---|---|
| **2** | `C1400a`（带锚点的迭代器，需要 pivot 节点 `n9`） | 有 pivot，否则退回 `C1418s` |

### 2.4 白茶做成了什么

白茶 `NavigationMode.kt:127~133`：

```kotlin
    LIST_TRAVERSAL("列表遍历", 16, 16, NavigationKind.TRAVERSAL),
    ROW_AND_COLUMN_TRAVERSAL("行列遍历", 31, 31, NavigationKind.TRAVERSAL),
    VERTICAL_TRAVERSAL("垂直遍历", 17, 17, NavigationKind.TRAVERSAL),
```

然后 `TraversalStrategyFactory.create()` 按这个值 `when` 出 `ListTraversalStrategy` /
`GridTraversalStrategy` / `VerticalTraversalStrategy`。

**问题**：天坦的 `i10` 取值里根本没有 16/17/31 这三个数会走到「列表/垂直」策略 ——
16/17/31 落进 `h()` 的 `else` 分支，拿到的是 **`C1418s`（默认）或 `C1403d`**，
真正的差异全在 `t(i10)` 的**过滤器**上。

白茶把「过滤器差异」实现成了「遍历器差异」。
这在**结果上有时候能凑对**（都限制了只停在某些节点），但机制不同：

* 天坦：遍历顺序**不变**（始终是按树序 + 几何排序的默认遍历），只是**跳过不符合过滤器的节点**。
  于是「列表遍历」下，焦点仍能正确地按视觉顺序走，只是不停在非列表项上。
* 白茶：换了一个**遍历器**，`ListTraversalStrategy.next()` 用
  「找容器 → 取容器内可聚焦子项 → 按 idx±1 走」，
  这与 `TatansTraversal`（天坦默认遍历器）的排序/可聚焦判定是**两套独立实现**。

### 2.5 实测结论（**已用真实树结构验证，不是推断**）

本轮引入 `FakeNode`（可实例化 + 完整父子结构）后，
`TraversalStrategyTreeTest` 用真实三层/四层树实测（8 条全绿）：

| 策略 | 深层节点 item(3) 能否到达 | 依据 |
|---|---|---|
| `DefaultTraversalStrategy`（= 天坦默认 `C1418s`） | **能** | `defaultTraversal_finds_deep_nodes` 实测通过 |
| `ListTraversalStrategy.getFocusableChildren()` | **不能**（只下钻一层） | `listTraversal_start_misses_deep_nested_items` 锁定当前行为 |

`getFocusableChildren()`（`TraversalStrategy.kt:166~179`）的规则是：
`child` 可聚焦就直接收，**不再看它的子节点**；只有 `child` 不可聚焦才下钻一层，
**孙节点不再看**。所以「分组有文本、项在分组内」这种结构里，
项会被整体跳过。

**重要更正**：我在写本节初稿时把这一条写成「推断」。实测后确认：
* 「默认遍历能到达深层」——**成立**（有测试为证）；
* 「列表遍历漏深层」——**成立**（有测试为证）；
* 但**「真机上一定会出问题」仍属未验证** —— 因为要触发它，用户必须先切到
  「列表遍历」导航模式，且恰好遇到「可聚焦分组包着可聚焦项」的结构。
  这两条都**没有真机证据**。保留为待验证项，不写成已确认缺陷。

**处置**：这是一次**架构级改动**（要把 `traversalType` 拆成「策略选择」与「过滤器选择」两个参数），
不是本轮「地基」范围内能安全做的。**记录在案，标注为真机验证优先级最高的一项**，
先等用户真机反馈「列表遍历 / 行列遍历 / 垂直遍历」三个模式的实际表现再定夺。

## 三、`ListTraversalStrategy.start()` 与天坦默认实现不符（P1）

白茶 `TraversalStrategy.kt:140~147`：

```kotlin
    override fun start(root: AccessibilityNodeInfo, direction: Int): AccessibilityNodeInfo? {
        val container = findScrollableContainer(root) ?: root
        val children = getFocusableChildren(container)
        return if (direction == TraversalStrategy.DIRECTION_NEXT) {
            children.firstOrNull()
        } else {
            children.lastOrNull()
        }
    }
```

* `next()`（:109~138）的移动规则是「找容器 → 在**容器内子项序列**里 idx±1」，
  容器内到边界时才 `traversal.next/previous(node)`。
* `start()` 返回 `children` 的 first/last —— 这是**容器内子项序列**的端点，与 `next()` 的规则**自洽**。

所以 `start()`/`next()` 内部是一致的，**但整体语义与天坦不同**（见第二节）。
单独看这一个函数**不能判为 bug**，故降级为「与天坦机制不同」，并入第二节统一处置。

## 四、`CachedTraversalStrategy`：`start()` 与 `next()` 的降级条件不一致（P2，当前不可达）

白茶 `TraversalStrategy.kt:255~275`：

```kotlin
    override fun next(node: AccessibilityNodeInfo, direction: Int): AccessibilityNodeInfo? {
        ensureBuilt()
        val list = flattened
        if (list == null || list.size < MIN_NODES_FOR_CACHE) {   // ← 节点少 → 退回默认策略
            return fallback.next(node, direction)
        }
        val idx = indexMap[node] ?: return fallback.next(node, direction)
        ...
    }

    override fun start(root: AccessibilityNodeInfo, direction: Int): AccessibilityNodeInfo? {
        ensureBuilt()
        val list = flattened ?: return null
        return if (direction == TraversalStrategy.DIRECTION_NEXT) {
            list.firstOrNull()                          // ← 没有降级判断
        } else {
            list.lastOrNull()
        }
    }
```

`next()` 有 `list.size < MIN_NODES_FOR_CACHE → fallback` 的降级，
`start()` **没有**。同一棵树、同一个策略实例上，两者会给出**不同的遍历空间**：
`start()` 从缓存序列取端点，`next()` 走 `fallback`。

【为何当前不可达】`grep` 全项目：`TYPE_CACHED` 只在
`TraversalStrategy.kt:409`（定义）与 `:453`（工厂分支）出现，
`NavigationMode` 里所有模式的 `traversalType` 取值是 `0 / 16 / 17 / 31`，
**没有任何调用方会传 2**。故 `CachedTraversalStrategy` 目前是死分支。

**处置**：不修（改死代码无收益、无法真机验证）。**记录在案**，
将来若真要启用索引缓存策略，必须先对齐这个降级条件。

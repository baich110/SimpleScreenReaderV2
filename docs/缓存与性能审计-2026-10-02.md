# 缓存与性能审计（2026-10-02 第四轮）

> 方法：对照 TalkBack 的框架代码，审查本项目的热路径与缓存设计。

## 修复 1：遍历索引缓存语义错误（P0）

**文件**：`TatansTraversal.kt` — `indexOf()`

### 问题

上一轮我把这个缓存的键从 `parent.hashCode()`（内容哈希）
改成了 `System.identityHashCode(parent)`（对象身份），以为是对的。
**实际上是错的。**

因为这两个键的**失效行为完全不同**：

| 键类型 | 子节点增删后 | 结果 |
|---|---|---|
| 内容哈希（天坦用法）| 哈希值变化 → 缓存不匹配 → **自动失效** | ✅ 安全 |
| 对象身份（我改的）| 身份恒定 → 缓存仍命中 → **用旧的中心索引做搜索** | ❌ 索引错位 |

对象身份在对象存活期间恒定，树结构变化后缓存**不会失效**，
双向扩展搜索会以过期的中心点为基准 → 搜不到就漏掉 → **焦点跳错位置**。

### 天坦为什么用内容哈希

`d7/C1423r.p()` 用 `wVar.hashCode()`。这不是随手写的 ——
内容哈希自带「结构变化检测」能力，等于给缓存加了自动失效。

### 修复

```kotlin
val hash = parent.hashCode()                    // 回到内容哈希（自失效）
if (hash == cacheParentHash &&
    count == cacheChildCount &&
    Companion.cacheGeneration == generation)    // ★ 再加代数双保险
```

同时新增 `invalidateIndexCache()`，挂到 4 个失效钩子：
- 窗口状态变化
- 窗口集合变化
- 内容变化
- 横竖屏切换

### 教训

**缓存的键语义决定了失效策略**。用身份做键 ≈ 关掉了自动失效，
必须配显式失效钩子；用内容做键则天然自失效，但代价是哈希碰撞风险。
设计缓存时必须先问：**这个键在数据变化时会变吗？**

## 修复 2：角色判定的反射热路径（P0，性能）

**文件**：`NodeRoleHelper.kt` — `classNameExtends()`

### 问题

```kotlin
private fun classNameExtends(cls: String?, parent: String): Boolean {
    return try {
        val c = Class.forName(cls)        // ← 每次调用都执行
        val p = Class.forName(parent)     // ← 父类固定却每次重查
        p.isAssignableFrom(c)
    } catch (e: Throwable) { false }
}
```

`roleOf()` 是**每次节点访问**都会走的路径（滑动浏览的每个节点、
遍历的每个候选、合成的每个片段）。而 `Class.forName` 会触发类加载，
需要拿 ClassLoader 锁 —— 在大列表快速滚动时是明确的卡顿来源。

### 修复

新增 `ClassLoadingCache`（对应 TalkBack `ClassLoadingCache`，但更强）：

| 能力 | TalkBack | 本项目 |
|---|---|---|
| 类对象缓存 | ✅ | ✅ |
| 失败结果缓存 | ✅（存 null）| ✅（哨兵 `NULL_CLASS`，语义更清晰）|
| 线程安全 | 普通 HashMap | **ConcurrentHashMap**（roleOf 可能被主线程与无障碍线程同时调用）|
| 继承关系结果缓存 | ❌ | ✅ **额外缓存** `isAssignableFrom` 结果 |
| 容量控制 | 无 | ✅ 上限 + 淘汰 |

第二行是关键的：本项目的事件处理在主线程、事件回调在无障碍线程，
`roleOf()` 两边都会调用，TalkBack 的单线程 HashMap 假设在这里不成立。

## 缓存体系全清单（8 处）

| 缓存 | 键语义 | 失效方式 | 风险等级 |
|---|---|---|---|
| `NodeCache.childrenCache` | 身份 | 代数自增 | 已挂钩子 ✅ |
| `NodeCache.focusCache` | 身份 | 代数自增 | 已挂钩子 ✅ |
| `NodeCache.textCache` | 身份 | 代数自增 | 已挂钩子 ✅ |
| `TatansTraversal.cache*` | 内容哈希 | 内容变化自失效 + 代数 | 本轮修复 ✅ |
| `NodeBoundsCalculator.boundsMap` | 身份 | `clear()` | 已挂钩子 ✅ |
| `ClassLoadingCache.classCache` | 类名 | 容量淘汰 | 无状态依赖 ✅ |
| `ClassLoadingCache.assignCache` | 子+父类名 | 容量淘汰 | 无状态依赖 ✅ |
| `NavigationManager.filterCache` | 导航枚举 | 进程生命周期 | 无状态依赖 ✅ |

**结论**：所有「身份键」缓存均已挂失效钩子；「内容/字符串键」缓存无需失效钩子。

## 后续建议

1. 给缓存挂钩子这件事**应做成约定而非记忆** —— 已在架构文档中记录。
   可考虑加一个 `CacheRegistry`，让所有缓存注册进来，一处调用全部失效，
   避免将来新增缓存忘了挂钩子。
2. `SoundManager.soundIdCache` 无容量上限，若音效资源很多可能增长 —— 低风险，暂不动。

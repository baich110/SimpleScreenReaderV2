**发现**：本工程 `testOptions.unitTests.isReturnDefaultValues = true`，

| 调用 | 返回值 |
|---|---|
| `new AccessibilityNodeInfo()` | `null` |
| `isVisibleToUser()` | `false` |
| `getText()` | `null` |

**后果**：任何依赖这些判定的被测代码，在测试里**永远走 false 分支**。

`equals` 故意保持**内容相等**语义 —— 因为 `FocusSearch` 环检测用 `HashSet`，

## ★ 本轮教训：我的两次错误结论

**① 「等价变异」的误判（第十六轮）**
变异「前向滚动用累计 → 改用本次位移」**逃逸**后，
我论证它是等价变异（语义不可观测），并据此写了一条「两者恒等」的测试。
**穷举验证后发现 9900 组可观测差异**，最小样本：
```
第1笔(-50,-50) 累计(-50,-50) 未达阈值
第2笔(-200,10) 累计(-250,-40) 达阈值
  原版(累计): -250>0 || -40>0 → false
  变异(本次): -200>0 || +10>0 → true   ← 回弹被误判成功
```
⇒ **「我觉得它是等价变异」不成立，必须穷举或构造验证。**

**② 「重入死锁」的误判（第十七轮）**
我断言「`clear()` 锁内调 `onDone` ⇒ 回调重入即死锁」，写了两条测试 ——
**两条都通过**。JVM `synchronized` 是**可重入锁**，同线程重入不阻塞。
真正的问题是**跨线程**与**持锁执行耗时外部代码**。
⇒ 理由站不住的部分已从结论中剔除，只保留可验证的语义。

## ★ 本轮纪律教训：计数式断言抓不住「少一个」

**第二十轮**：`addAccessibilityAction` 计数 ≥ 6 的断言，

> 「计数达标」≠「每一项都做了」。
> 断言必须落在**具体的配对/每一项**上。

## ★ 本轮方法论收获

**并发缺陷的复现，必须让共享状态被写入不同的值。**

第一版测试用**同一个固定时间值**并发格式化 → 错乱 0 次、异常 0 次（没复现）。
原因：内部 `Calendar` 被反复写入**相同的值**，线程互踩也踩不出差异。
改成**不同时间值** + 提高并发后立即复现（22 万次错乱）。

> 用不变的值去压测共享可变状态，等于什么都没测。

## ★ 系统性扫描的第二次应用（第一次是「值类型缺 equals」）

## ★ 「@Volatile 变异逃逸」的第三次防御

本项目曾因「断言文件含 `@Volatile`，而**注释里**也有这个词」导致变异逃逸。
本轮断言改为：**紧邻上一行**必须是 `@Volatile`，且断言前**剥掉注释**。

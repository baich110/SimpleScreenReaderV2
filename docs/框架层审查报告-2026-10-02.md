> 「测试通过」不等于「逻辑正确」——
> 如果被测代码依赖的类在测试环境中是空壳，测试会给出虚假的安全感。
> 判断方法：在测试里打印被测数据。

**单测查不出来**（引擎测试全绿），**代码审查也容易漏**（代码写得对），只有专门审计「接线」才能发现。

### 2.1 P0-1 只修了一半

#### 现状

`NavigationMode` 加了 `traversalType` 字段 ✅

```kotlin
DEFAULT("默认", 0, 0, NavigationKind.GRANULARITY),
WORDS("字词", 2, 0, NavigationKind.GRANULARITY),      // ← 导航码 2，遍历器码 0 ✅
CONTROLS("控件", 8, 0, NavigationKind.FILTER),        // ← 导航码 8，遍历器码 0 ✅
VERTICAL_TRAVERSAL("垂直遍历", 17, 17, NavigationKind.TRAVERSAL),
```

**但取值函数没改：**

```kotlin
// NavigationMode.kt:327
fun strategyTypeCode(): Int = current.typeCode      // ★ 还是返回导航码
//                              ^^^^^^^^^^^^^^^^ 应该是 current.traversalType
```

#### 实际影响（实测推演）

| 导航 | typeCode | traversalType | 实际用 | 应该用 |
|---|---|---|---|---|
| 默认 | 0 | 0 | Default | Default ✅ |
| **字词** | **2** | **0** | ❌ **`CachedTraversalStrategy`** | Default |
| **控件** | **8** | **0** | ❌ **`GridTraversalStrategy`** | Default |
| 列表遍历 | 16 | 16 | List | List ✅（凑巧） |
| 行列遍历 | 31 | 31 | RowColumn | RowColumn ✅（凑巧） |
| 垂直遍历 | 17 | 17 | Vertical | Vertical ✅（凑巧） |

**「列表/行列/垂直」现在是对的，但那是**凑巧**（它们的 `typeCode == traversalType`）。**

**「字词」和「控件」还是错的。**

#### 为什么漏了

**第六轮对标文档里写：**

> 白茶策略类型码 `TYPE_DEFAULT=0 / TYPE_CACHED=2 / TYPE_GRID=8 / TYPE_LIST=16 / TYPE_ROW_COLUMN=31 / TYPE_VERTICAL=17` 与天坦完全一致。

**核对的是「Factory 认的类型码」和「天坦策略类型码」—— 这部分确实一致。**

**但漏了一个环节：`NavigationMode.typeCode` → `strategyTypeCode()` → `Factory` 这条链路上，中间那个函数还在传旧值。**

#### 为什么测试没抓到

**写了完整的 P0-1 回归测试（`NavigationTraversalTypeTest`），但测的是**字段值**：**

```kotlin
@Test
fun words_navigation_must_not_use_cached_traversal() {
    assertEquals(2, NavigationMode.WORDS.typeCode)
    assertEquals(TraversalStrategyFactory.TYPE_DEFAULT,
                 NavigationMode.WORDS.traversalType)   // ← 测字段，字段是对的
}
```

**唯一测 `strategyTypeCode()` 的那条，用的是 `LIST_TRAVERSAL`：**

```kotlin
@Test
fun strategy_type_code_follows_mode() {
    m.setMode(NavigationMode.LIST_TRAVERSAL)
    assertEquals(16, m.strategyTypeCode())    // ← 16 既是导航码也是遍历器码
}
```

**这条**碰巧通过** —— 因为 `LIST_TRAVERSAL.typeCode == traversalType == 16`。如果测的是 `WORDS`，就会失败。**

**这是个典型的「测试假阳性」：测了一个两值相等的特例。**

#### 修复

**一行：**

```kotlin
// NavigationMode.kt:327
fun strategyTypeCode(): Int = current.traversalType
```

**加一条测试（覆盖真正会暴露问题的导航）：**

```kotlin
@Test
fun strategy_type_code_uses_traversal_type_not_navigation_code() {
    val m = NavigationManager()

    // WORDS：导航码 2 会撞 TYPE_CACHED，必须返回 0
    m.setMode(NavigationMode.WORDS)
    assertEquals(
        "「字词」必须返回默认遍历器码 0，不能返回导航码 2",
        TraversalStrategyFactory.TYPE_DEFAULT,
        m.strategyTypeCode()
    )

    // CONTROLS：导航码 8 会撞 TYPE_GRID，必须返回 0
    m.setMode(NavigationMode.CONTROLS)
    assertEquals(
        "「控件」必须返回默认遍历器码 0，不能返回导航码 8",
        TraversalStrategyFactory.TYPE_DEFAULT,
        m.strategyTypeCode()
    )
}
```

### 2.2 BUG-1 粒度遍历事件读整段文本

**（`extractTraversedText` 未接线）**

#### 现象

用户切到「按字」导航，按「下一个字」，**念的是整段文本，不是当前那个字。**

#### 代码（`AccessibilityEventHandler.kt:297`）

```kotlin
AccessibilityEvent.TYPE_VIEW_TEXT_TRAVERSED_AT_MOVEMENT_GRANULARITY -> {
    val text = event.text?.joinToString("")?.trim().orEmpty()   // ★ 读整段
    if (text.isNotEmpty()) {
        log("粒度遍历: $text")
        speech.speak(text, interrupt = true)                     // ★ 念整段
    }
}
```

**问题**：`event.text` 是**整个节点的文本**，不是「当前粒度单元」。

**正确做法**：`GranularityMover.extractTraversedText()` 已经写好了 —— 它优先用事件文本，退化时用 `event.fromIndex` / `event.toIndex` 从节点文本里切片。**但它没有被接线。**

#### 修复

```kotlin
AccessibilityEvent.TYPE_VIEW_TEXT_TRAVERSED_AT_MOVEMENT_GRANULARITY -> {
    // ★ 改用 extractTraversedText —— 它会从 fromIndex/toIndex 切出当前粒度单元
    val text = GranularityMover.extractTraversedText(event)
    if (!text.isNullOrEmpty()) {
        log("粒度遍历: $text")
        speech.speak(text, interrupt = true)
    }
}
```

**这是个真 bug，影响 P0-2 的完整性** —— 粒度导航的「移动光标」修好了（走系统 API），但「朗读当前单元」没接上。

### 2.3 BUG-2 输入法上屏 API 是死代码

**（无外部入口）**

#### 现状

`ReaderAccessibilityService` 有两个公开方法：

```kotlin
fun commitImeCandidate(text: String): Boolean     // 1132 行
fun canCommitImeText(): Boolean = imeAdapter.canCommit()   // 1155 行
```

**但整个 App 里没有调用方，也没有对外入口：**

```
Manifest 里只有：
  - 1 个 service（无障碍服务）
  - 2 个 activity（MainActivity / TtsSettingsActivity）

没有：
  - AIDL 接口
  - BroadcastReceiver
  - ContentProvider
  - 第二个 Service
```

#### 天坦是怎么做的

`net/tatans/soundback/TatansImeService.java`（457 行）：

```java
public final class TatansImeService extends Service {
    // AIDL 接口：net.tatans.soundback.ITatansImeConnection
    public static final class b extends d.a {     // d.a = AIDL Stub
        public boolean F(IBinder iBinder, int i9, String str) { ... }
        public int L(IBinder iBinder) { ... }
        public void M(IBinder iBinder, int, int, int, int) { ... }
        public boolean O(IBinder iBinder, List list) { ... }
        public void Q(IBinder iBinder, c cVar) { ... }
        public void U(IBinder iBinder, String str, int, int) { ... }
        // ... 十几个 AIDL 方法
    }
}
```

**天坦输入法通过 `bindService` 连到这个服务，调用 AIDL 方法让读屏播报候选词、上屏文本。**

**我们的 `commitImeCandidate` 定义在无障碍服务上，但无障碍服务是系统绑定的（`BIND_ACCESSIBILITY_SERVICE`），第三方 App 无法通过 `bindService` 拿到它的 Binder。**

**所以这两个方法是**永远调不到的死代码**。**

#### 修复方案

**方案 A：加独立的 IME 服务 + AIDL（照抄天坦）**

```kotlin
// ImeConnectionService.kt
class ImeConnectionService : Service() {
    private val binder = object : IImeConnection.Stub() {
        override fun commitCandidate(text: String): Boolean =
            ReaderAccessibilityService.instance?.commitImeCandidate(text) ?: false

        override fun canCommit(): Boolean =
            ReaderAccessibilityService.instance?.canCommitImeText() ?: false

        override fun speakCandidates(text: String) { ... }
    }

    override fun onBind(intent: Intent): IBinder = binder
}
```

```xml
<!-- AndroidManifest.xml -->
<service
    android:name=".core.ImeConnectionService"
    android:exported="true"
    android:permission="net.baicha.reader.permission.IME_CONNECTION">
    <intent-filter>
        <action android:name="net.baicha.reader.IME_CONNECTION" />
    </intent-filter>
</service>
```

**方案 B：暂时标注为「待接线」**

如果短期不做输入法对接，**留着死代码会误导**（看起来「输入法适配已完成」）。

**建议**：加注释说明「需要外部 IME 通过 AIDL 调用，当前无对接方」。

## 三、工作模式问题（五个严重问题）

**这节审的是「你怎么工作」，不是「你写了什么」。**

**为什么同样的错误会重复出现？为什么测试全绿但功能没生效？为什么自己写了「待验证」却继续往前冲？**

**这些不是代码问题，是工作模式问题。而工作模式问题会**持续产生**代码问题 —— 修一个，下一个还会来。**

### 🔴 问题 1：「验证」= 编译通过 + 单测全绿（最严重）

**证据 —— 每一轮报告，验证章节都是这个格式：**

```markdown
## 五、验证
- `testDebugUnitTest` + `assembleDebug` 全绿
- 465 个单测 / 47 个测试类，0 失败
- 提交：4f317be
```

**问题在哪：**

**你写的测试，测的是「你自己写的代码」—— 它证明不了「代码接对了」。**

**P0-1 就是活证据：**

| 你的验证 | 实际 |
|---|---|
| `traversalType` 字段值正确 ✅ | 字段确实对 |
| `usesTraversal` 属性正确 ✅ | 属性确实对 |
| 465 个测试全绿 ✅ | 测试确实全过 |
| **但 `strategyTypeCode()` 返回旧值** | **功能是坏的** |

**你的测试全绿，功能是坏的。这中间没有任何一个环节能发现。**

**为什么：**

```
你写代码 → 你写测试 → 测试通过 → 你认为完成
   ↑                                    ↓
   └────────── 同一个大脑 ──────────────┘
```

**同一个大脑，同样的理解偏差，测试和实现会一起错。** 这叫**确认偏误**（confirmation bias）。

**建议：**

**① 验证要分三层，不能只有一层：**

```
第一层：单测（你已经在做）
  → 证明「逻辑分支正确」

第二层：接线核查（你做了「接线审计」，但不够）
  → 证明「代码被调用了」
  → 但还要证明「调用时传的参数是对的」

第三层：端到端验证（你一直没做）
  → 证明「用户听起来是对的」
  → 读屏软件，最终判据是「耳朵」不是「测试」
```

**② 每轮报告，「验证」章节必须写清楚：**

```markdown
## 验证

### 已验证（有证据）
- 单测：465 通过 / 0 失败（`testDebugUnitTest`）
- 编译：BUILD SUCCESSFUL
- **接线核查**：新增/修改的每个方法，列出调用方（第 X 行）
- **参数核查**：调用方传的参数，与方法的期望一致

### 未验证（明确列出）
- 真机行为：粒度导航是否真的移动光标 → **未验证**
- 真机行为：跨窗口导航是否真的能走出弹窗 → **未验证**

### 验证不了的（说明原因）
- 输入法上屏：需要真实输入法 App 配合 → 单测覆盖不到
```

**关键：把「未验证」写出来，而不是含糊带过。**

### 🔴 问题 2：自己写了「待验证」，然后继续往前冲

**证据 —— 第二轮报告里写了（`焦点导航对标-第二轮-2026-10-02.md:709`）：**

```markdown
## 仍需真机验证 ⚠️
已连续多轮未做真机验证。框架层已改到 47 个类 / 14945 行，

1. 粒度导航是否真的移动光标并朗读新片段（P0-2 修复的最终验收）
2. 窗口导航（P0-3 新实现）
3. 垂直遍历（P0-1 新增的 VerticalTraversalStrategy）
4. 压缩包 / RAR5 等依赖系统能力的功能

> 单测能证明「逻辑分支正确」，不能证明「读屏用户听起来是对的」。
```

**然后呢？**

**接着做了第四轮、第五轮、第六轮、第七轮 —— 加了 `ScrollToPosition`、`WebElementNavigator`、`NavigationStore`、`CursorRepositioner`、`ImeAdapter`、`WindowClassifier`、`NavigationLabel`、进度播报……**

**从 14945 行做到 16132 行。**

**而那个「待验证」清单，一项都没验。**

**问题在哪：**

**这不是「忘了」，是**结构性**的 —— 工作循环是「发现缺口 → 补缺口 → 写文档」，**没有「验证上一批」这个环节**。

```
你的循环：
  发现缺口 → 补 → 写文档 → 发现新缺口 → 补 → 写文档 → ...

应该是：
  发现缺口 → 补 → 写文档 → ★ 验证上一批 ★ → 发现新缺口 → ...
```

**后果：**

**未验证的改动会**累积**。现在有 8 项待验证，每项都可能是坏的。**

**如果第 1 项（粒度导航）是坏的，那你在它上面建的 `CursorRepositioner` 也是白做。**

**建议：**

**① 建立「验证债」概念**

**像技术债一样，验证债也要记账：**

```markdown
## 验证债（截至第八轮）

| # | 改动 | 提交 | 状态 | 风险 |
|---|---|---|---|---|
| 1 | 粒度导航（系统光标 API） | 9407f61 | ⏳ 待真机 | 高（P0 修复的验收） |
| 2 | 跨窗口导航 | 045a8ed | ⏳ 待真机 | 高 |
| 3 | 垂直遍历 | 9407f61 | ⏳ 待真机 | 中 |
```

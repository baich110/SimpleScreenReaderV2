## 一、埋点位置（本轮新增 `PerfCounters`）

| 指标 | 埋点位置 | 说明 |
|---|---|---|
| 导航耗时 | `FocusManager.moveFocus()` 最外层 try/finally | 覆盖全部退出路径，与 `ShouldFocusNode.resetOperationScope()` 同一处 |
| 缓存命中/未命中 | `NodeCache.getOrCompute` | 判定缓存的核心读写点 |
| 事件处理 | `EventDispatcher.dispatch()` 入口 | — |
| 事件丢弃 | `EventDispatcher` 两处去重返回点 | 丢弃是**静默**的，用户只感觉「漏读了」 |

### 为什么不用现成性能框架

读屏跑在无障碍服务里，**每个触摸/滑动/焦点事件都走这条路径**，
测量开销必须趋近于零：

- 不在热路径分配对象（无 boxing、无字符串拼接）
- 计数用 `Long` 累加 + 原生 `int`
- 全部字段 `@Volatile`，读路径无锁

天坦与 TalkBack 都**没有**这类埋点（靠 Log 手工排查），
这是本项目独有的一层。

## 三、怎么取数（真机步骤）

### ① 导航耗时 + 缓存命中率

```bash
# 1. 触发一轮测量重置（或重启服务）
# 2. 在任意 App 里滑动浏览 100 次左右
# 3. 看日志里的 PerfCounters.report() 输出
```

预期输出形如：
```
【性能基线】
导航：100 次，平均 12ms，最大 45ms
缓存：命中 850 / 未命中 120，命中率 87.6%
事件：处理 320 / 丢弃 15，丢弃率 4.5%
```

### ② 内存

```bash
adb shell dumpsys meminfo com.baicha.reader | head -20
```

### ③ 冷启动

看 `ReaderLog` 里服务 `onServiceConnected` 到首次可用的时间差。

## 五、如何判断性能回归

基线的用途是比较。建立基线后，每次改动可对比：

| 场景 | 看什么 | 恶化信号 |
|---|---|---|
| 改了缓存策略 | 命中率 | 命中率下降 > 10% |
| 改了遍历逻辑 | 平均导航耗时 | 耗时上升 > 20% |
| 改了事件分发 | 丢弃率 | 丢弃率上升 > 5% |

`PerfCounters.reset()` 用于「开始新一轮测量」——
服务是常驻的，计数器会一直累积，必须有清零点。

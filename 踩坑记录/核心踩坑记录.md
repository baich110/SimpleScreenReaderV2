## 一、四大根因（反复踩的坑）

### 1.1 `IdentityHashMap` 做节点映射 → 100% 失效

**现象**：
```
建树完成: 95 个节点, root=「(无文本)」(FrameLayout, ch=2)
❌ 下一焦点 | 失败 ← 遍历无果；诊断=访问 0
```

**根因**：
`AccessibilityNodeInfo` 每次 `getChild(i)` / `getFocused()` 都返回**新对象**（identity 不同但内容相同）。
`OrderedTraversalController.nodeMap` 用 `IdentityHashMap` → `nodeMap[edit/EditText]` 未命中 → `next()` 直接返回 null。

**修复**：
`nodeMap` 从 `IdentityHashMap` 改为 `HashMap`（内容 equals 比较）。
对齐 TalkBack 的 `OrderedTraversalController.nodeTreeMap`（`Map<AccessibilityNodeInfoCompat, WorkingTree>`）。

**教训**：
> **`AccessibilityNodeInfo` 的 identity 比较永远不可靠。**
> 任何时候要"记住一个节点"，都必须用内容比较（`equals` / 内容指纹）。

### 1.2 `searchFocus` 只走一步 → 第一步不可聚焦就失败

**现象**：
```
next(EditText, ch=4) → View(ch=0)   ✅ 走通了
❌ 下一焦点 | 失败 ← 设焦点失败（performAction 返回 false）
   搜索=「(无文本)」(?/View) 可达性=退到父节点
```

**根因**：
遍历器返回的是**未过滤**节点（TalkBack 设计如此，过滤由上层做）。
原代码 `return strategy.next(start, direction)` 只走一步，第一步返回的节点如果不可聚焦就直接失败。

**修复**：
照抄 TalkBack `TraversalStrategyUtils.searchFocus()` 的 `do-while` 循环 + `seenNodes` 防环：

```java
do {
    seenNodes.add(targetNode);
    targetNode = traversal.findFocus(targetNode, direction);
    if (seenNodes.contains(targetNode)) return null;   // 防环
} while (targetNode != null && !nodeFilter.accept(targetNode));
return targetNode;
```

**验证**：日志出现 `searchFocus: 走了 32 步 → EditText`（跳过了 31 个不可聚焦节点）。

### 1.3 播报去重用 `identityHashCode` → 一会儿播一会儿不播

**现象**：
```
08:19:27.740 ✅ 下一焦点 | 通过 → 「(无文本)」(?/View)   ← 焦点是空 View
08:19:27.741 speak 请求: '...'                          ← 播报却是另一个节点的文本
```
用户反馈："一会儿有朗读，一会儿没有朗读"

**根因**：
两个问题叠加：
1. **播报内容跟焦点对不上** —— 焦点是 `(无文本)View`，播报却是 `deepseek-v4-flash`（用了另一个节点的文本）
2. **speak 被丢弃** —— 14~27ms 内同文本被请求两次，第二次触发 120ms 阈值把第一次干掉
3. **去重用 `identityHashCode`** —— 同一节点不同对象，去重失效

**修复**：
播报去重从 `identityHashCode` 改为**内容指纹**（`NodePath.fingerprintOf(node)`）。

**教训**：
> **播报去重必须用内容指纹，不能用 identity。**
> 这是同一个坑踩了第二次（第一次在遍历器）。

### 1.4 抄天坦的私有补丁 → 抄错版本，必错

**现象**：
真机 dump 验证：20 个空容器全部被放行 → 焦点停在空容器 → 下次从空容器出发找不到东西 → 卡死。

**根因**：
抄的天坦反编译函数是**旧版**，实际生效的是新版，两个函数分支写法完全不同：

| 版本 | 位置 | 逻辑 |
|---|---|---|
| **旧版（抄错的）** | `d7/C3678d.java` (FocusFinder 废弃路径) | `if (childCount == 0 \|\| hasContentOrActionableChild) return true` —— 对「有可见子但自己没内容」的容器**放行** |
| **新版（实际生效）** | `utils/AccessibilityNodeInfoUtils.java:974~984` | `if (!hasVisibleChildren) return true; if (hasSomethingToSpeak) return true; return false` —— **有子但没内容 → 拒绝** |

旧版还有一处致命早退：`if (node.childCount == 0 || p(node)) return true` —— `p(node)` 对「有可聚焦子节点」的容器返回 true，在到达主判分支之前就 return true。

**修复**：
改用新版判定逻辑（`hasVisibleChildren` / `hasSomethingToSpeak` 替代 `hasContentOrActionableChild`），并移除 `p(node)` 早退分支。

**验证**：真机 dump 验证 20 个空容器全部走「有子+没内容」分支被正确拒绝，**20 → 0**。

**教训**：
> **天坦的 `shouldFocusNode` 是 2000+ 行的特定版本私有补丁，脱离上下文抄必错。**
> 要抄就抄 TalkBack 官方 `AccessibilityNodeInfoUtils.shouldFocusNode()` 七步链。

## 二、TalkBack 七步判定链（正确参照）

来源：`/home/talkback/utils/src/main/java/com/google/android/accessibility/utils/AccessibilityNodeInfoUtils.java`

```
① node == null → false
② WebView 支持 web actions → 委托 WebView 容器
③ !isVisible(node) → false
④ isPictureInPicture(node) → true
⑤ areBoundsIdenticalToWindow(node) && childCount > 0 && !isFocusableOrClickable(node) → false
   （窗口级容器拒绝）
⑥ accessibilityFocusable = isFocusableOrClickable(node) || (isTopLevelScrollItem(node) && isSpeakingNode(...))
⑦ if (!checkChildren) return accessibilityFocusable（递归终止）
⑧ accessibilityFocusable 为真时：
   - 叶子（childCount==0）→ true
   - isSpeakingNode → true
   - 否则 → false
```

对应关系：
- 天坦 `hasSomethingToSpeakInternal` ≡ TalkBack `isSpeakingNode`
- 照新版天坦抄即对齐 TalkBack 语义

## 三、焦点生命周期管理（未解决的架构问题）

### 3.1 焦点震荡死循环

**现象**：
用户反馈："音效疯狂的在响，然后焦点在疯狂的落回"

**根因**：
`ScreenStateRecovery.recoverInternal()` 和 `FocusManager.applyFocus()` 之间**没有防回声/防互踢机制**：

```
1. ScreenStateRecovery 判定「窗口未获得焦点」→ 恢复焦点到第一个节点（菜单）
2. 用户滑动触发 applyFocus(新节点) → root.findFocus() 取到旧焦点（菜单）
   → 非同一节点 → performAction(ACTION_CLEAR_ACCESSIBILITY_FOCUS) 清掉菜单
3. 系统发 TYPE_VIEW_ACCESSIBILITY_FOCUS_CLEARED
   → ScreenStateRecovery 又判定「窗口未获得焦点」→ 又恢复
4. playFocusSound 在每个 FOCUSED 事件上都响 → 音效狂响
```

**真机日志证据**（50ms 内 6 次焦点跳变）：
```
07:11:35.614 窗口 812 未获得无障碍焦点         ← ScreenStateRecovery 触发
07:11:35.643 恢复焦点：路径未命中 → 取第一个
07:11:35.723 恢复焦点: 菜单
07:11:35.741 屏幕状态恢复: 已恢复焦点
07:11:35.770 屏幕状态恢复: 用户已操作，不抢焦点  ← 自相矛盾，抢完又说不抢
07:11:35.774 无障碍焦点: 菜单                  ← 又设一次
07:11:35.778 焦点清除                          ← 立刻被 applyFocus 清
07:11:35.784 无障碍焦点: 编辑框                 ← 又跳到别的
```

**关键代码缺陷**（`FocusManager.applyFocus()`）：
```kotlin
val cur = root?.findFocus(FOCUS_ACCESSIBILITY)
if (cur != null && (cur != node || force)) {
    cur.performAction(ACTION_CLEAR_ACCESSIBILITY_FOCUS)  // ← 清旧，触发 CLEARED
    node.performAction(ACTION_FOCUS)                     // ← 设新，触发 FOCUSED
}
```
无标记位/无回声屏蔽，每次都会给自身派发事件。

**`ScreenStateRecovery.userInteractedDuringTransition()`** 用 `lastActionTime <= screenTransitionStartTime` 判定，但 `screenTransitionStartTime` 每次 `onScreenStateChanged` 都会更新，时序错乱。

**状态**：⚠️ **未解决**。这是所有焦点问题的根源。

### 3.2 触摸/滑动焦点不互通

**根因**：
`speakFocus` 和 `speakHover` 各自独立获取焦点节点，**没有共享 focusNode**。
`focusNode` 的调用只在 `speakFocus` 里，`speakHover` 里没有。

**天坦的做法**：
不通过 `speakFocus` 的 `focusNode` 参数传递，而是通过 `M6.h.E(service, 1, false, false, false)` **主动请求无障碍焦点**。

**状态**：⚠️ 未解决（架构层面）。

## 四、其他踩过的坑

| # | 坑 | 说明 |
|---|---|---|
| 1 | **`pm install -r` 不杀进程** | 只替换 APK 文件，进程还跑旧代码。必须 `am force-stop` |
| 2 | **`NodeFilter.CachedFilter` 污染 `focusCache`** | 组合过滤器的结果会覆盖 `ShouldFocusNode` 的判定 → 焦点乱跳 |
| 3 | **Activity 属性初始化器用 `this` 当 Context** | attach() 前执行，base context 为 null → NPE，必须 `by lazy` |
| 4 | **`isVisibleToUser` 不能作焦点判定依据** | 滚动/动画中返回 false，但焦点已设上。可见性判定归 `ShouldFocusNode`，不归合成器 |
| 5 | **`speakNode` 在 text==null 且 role==null 时静默返回** | `roleName()` 对多种 ROLE 返回 null → 完全静默 |
| 6 | **`ShouldFocusNode.r()` 的 `prevBounds` 永远传 null** | 调用点用默认参数，第⑤步死代码 |
| 7 | **`ensureReachable()` 是空壳** | 只打日志不改变聚焦目标 |
| 8 | **防抖常量命名与逻辑相反** | BASE/FAST/RETRY 与数值大小关系错乱 |

## 五、最核心的结论

> ### TalkBack 的组件不能拆一个塞进自己的项目。
>
> `Compositor` / `OrderedTraversalController` / `AccessibilityNodeInfoUtils`
> 是**一整套互相咬合的设计**，拆开用必崩。

**项目暂停的根本原因**：抄了一半 + 自己发明，导致问题永远修不完。

**下一步路线**：直接修改 TalkBack 源码（`/home/talkback/`），不要自建。

## 六、方法论（用户反复强调的）

1. **实测 > 推理** —— 出问题就用真机日志/curl 验证，别靠猜
2. **两方对比** —— 用户原话："TalkBack 开源代码你他妈都看不明白吗？我一直强调两方对比"
3. **修完一个 bug 就全项目扫该模式** —— 同一处错误往往有多份拷贝
4. **服务能启动是前置条件** —— 三版静态检查全绿但真机崩溃的教训
5. **测试替身默认值必须悲观** —— 别让测试通过掩盖真机问题
6. **P0 真机跑通 > P1 矩阵覆盖** —— 矩阵测试是定位工具，不是刷数量
